# 獎項配置 · 重新設計提案

> 使用者的原話：「第一張圖的獎項配置，我覺這介面有點太亂了，說明也不夠直接易懂，
> 再來就是一直選越多卡片就會一直往下無限延伸，請問有什麼新的辦法可以解決這樣做的問題？」

對應的檔案是 `src/pages/SellerNewPoolPage.vue`（獎項配置那一段，template 約 699–860 行、
CSS 約 1038–1105 與 1225–1256 行）。**這份提案沒有動 `src/` 底下任何一個檔案**，
產出只有這份 md 與 `docs/proto/prize-editor.html`。

---

## 0. 一句話

**把「一張卡一列表單」換成「一個賞別一組」**：賞別是分組，卡片是被指派進分組的縮圖，
買回價一個賞別填一次，逐張的例外設定藏在點一下才開的貼底面板裡。

實測（393×852，同一份資料）：

| | 現況 | 提案 | |
|---|---|---|---|
| 30 張卡時，獎項配置整段高度 | 7,457 px | 1,538 px | **−79%** |
| 30 張卡時，這一段要捲幾屏 | 8.8 屏 | 1.8 屏 | |
| 30 張卡時，這一段裡的可互動控制項 | 154 個 | 23 個 | **−85%** |
| 從 12 張加到 30 張，版面長高 | +4,045 px | **+0 px** | |

（「現況」量的是真的 `/seller/new` 頁面；「提案」量的是原型。原型裡也照真頁面的 CSS
重做了一份現況複本用來對照，兩者誤差 0.4–0.5%，見 §4.2。）

最後一列是重點：現況是 O(n)，提案是 O(賞別數)，而賞別數上限就是 6。
**「無限往下長」不是靠壓縮解決的，是靠換一個不隨張數成長的單位解決的。**

## 1. 先量，再說「亂」

### 1.1 怎麼量的

- headless Chromium（`playwright@1.62`，本 repo 既有相依），viewport **393×852**、DPR 2、`isMobile`。
- mock 模式（`VITE_API_URL` 留空），走真的 `/seller/new` 頁面。
- 為了穩定重現 1 / 5 / 12 / 30 四種張數，把 repo 複製到 scratchpad
  （`…/scratchpad/prizeia/app`），在**副本**裡加了一個 `?seed=N` 的種子鉤子，
  把 `form.prizes` 直接填成 N 列。渲染出來的仍然是原封不動的 `.prize-row`。
  **工作目錄的 `src/` 一個字都沒改。**
- 賞別分佈用頁面自己的猜法（第一張 A、其餘往下），數量一律 1。

補充兩個常被忽略的數字：

- **底部永遠被吃掉 127 px**：CardPicker 的貼底列 70 px ＋ 底部導覽 57 px（實測 fixed 定位）。
  一屏能用的其實是 725 px，所以「3.7 列」在真的用的時候是 **3 列**。
- **每一列高度 230 px 是四段疊出來的**（720px 以下的手機版把一列拆成四行）：
  卡圖／卡名區 48–58 ＋ 賞別 40 ＋ 數量 38 ＋ 參考價 38 ＋ 買回價 38 ＋ gap 24 ＋ padding 20。

### 1.3 一列裡有什麼

一列有 **8 個東西**，其中 **5 個可互動**：

| # | 元素 | 手機上的高度 | 標籤在哪 |
|---|---|---:|---|
| 1 | 卡片縮圖 | 47.5 px | — |
| 2 | 卡名 | — | — |
| 3 | 卡號／系列（＋鑑定編號） | — | — |
| 4 | 賞別下拉 | **40 px** | `aria-label`（看不見），值本身「A 賞」讀得出來 |
| 5 | 數量 | **38 px** | `placeholder="數量"` |
| 6 | 參考價 | **38 px** | `placeholder="參考價（選填）"` |
| 7 | 買回價覆寫 | **38 px** | `placeholder` 是**該賞別的金額**（例如「4,800」） |
| 8 | 刪除鈕 | **33 px** | `aria-label`（看不見） |

兩件量出來的事：

1. **表頭在手機上是 `display: none`**（`.prize-head`，實測確認），而 placeholder
   只在欄位空著時看得見。從卡冊挑進來的卡自帶參考價，所以那一格**一進來就有值**，
   placeholder 立刻消失。結果是：**一列 5 個控制項，在填好值的常態下，
   畫面上看得見的文字標籤是 0 個。** 唯一還讀得出自己是什麼的是賞別下拉，
   因為它的「值」剛好是「A 賞」。
   剩下三個數字框在畫面上長得一模一樣：一個填了 `28000`、一個空著顯示灰色的 `4,800`。
   使用者說的「太亂」，最硬的證據就是這一條。
2. **五個控制項全部低於 44 px 觸控下限**（40 / 38 / 38 / 38 / 33）。
   這一頁在 `769c4a2` 那一版把「還差什麼」清單補到 44 px 了，
   但獎項列這一段沒有被掃到。

### 1.4 說明文字量了什麼

| 位置 | 字數（去空白） | 它實際回答了什麼 |
|---|---:|---|
| 「買回價（依賞別）」下方 `.tbNote` | **103 字**（4 句） | 3 句在解釋**機制**（鎖死、寫進雜湊、從保留額出、不需要基準），回答「我該填多少」的只有半句 |
| 獎項表下方 `.twoCols` | **114 字** | 在解釋「參考價」與「買回價」**不是同一件事** |
| 挑卡區 `.pickNote` | 99 字 | 卡片身分會進承諾（這段是對的，不在這次的討論範圍） |

`.twoCols` 這 114 字最值得注意：**它存在的唯一理由，是版面把兩個意義完全不同的欄位
並排擺成兩個一樣的數字框。** 文字在補版面的洞。這種說明不論怎麼改寫都只會變短一點，
不會變好懂 —— 因為讀者要先在腦裡把兩個框對回兩段文字。

### 1.5 三個抱怨各自對應到哪一個數字

| 使用者說的 | 量出來是什麼 |
|---|---|
| 太亂 | 30 張時 154 個控制項擠在一段裡；一列 5 個控制項在常態下 0 個有可見標籤；3 個外觀相同的數字框意義完全不同 |
| 說明不夠直接易懂 | 103 字的說明裡只有半句在回答「我該填多少」；另一段 114 字純粹在補版面造成的誤解 |
| 越選越往下無限延伸 | 每張卡 +230 px，30 張 = 6,732 px 的列陣；整頁 11.6 屏；從挑完卡到送出鈕要捲 9.4 屏 |

## 2. 為什麼會長成這樣（這不是誰做錯）

現況是一張**表格**：一列一筆、欄位就是屬性。表格在桌機是對的 —— 實測 900px 以上
是七欄的 `grid-template-columns: 34px 1fr 88px 60px 84px 84px 32px`，一屏放得下十幾列。

問題出在 720px 以下：欄寬不夠，於是表頭被藏起來、一列被拆成四行。
**「把表頭藏起來」就是這個模型在手機上撐不住的自白** —— 表格的欄位靠表頭定義，
表頭沒了，欄位就只剩下形狀。剩下的三個數字框，形狀是一樣的。

所以這不是「再調一調間距」能解決的。要換的是**單位**。

## 3. 三個方向，以及各自的代價

### 方向一：每列收成一行摘要，點開才編輯

一列變成 `縮圖 · 卡名 · A賞 · 1籤 · 4,800`（約 56 px），點一下開貼底 `.sheet` 編輯。
站上已經有這個模式（`MyCardsPage.vue` 的出貨／回收面板、`LoginMethods.vue`）。

- 高度：30 張 ≈ 56×30 + 說明 ≈ **2,000 px**（vs 7,457）。
- 代價一：**仍然是 O(n)**。60 張（`CardPicker` 的上限）就回到 3,700 px，問題只是被推遲。
- 代價二：**沒有解決重複勞動**。同一個賞別的十張卡還是要點開十次才知道它們一樣。
- 代價三：多一層點擊才看得到金額，而金額正是這一頁最需要一眼掃過的東西。

### 方向二：賞別為主軸的分組指派（**推薦**）

獎項配置變成最多 6 張「賞別卡」（A / B / C / D / 最後賞 / 爆賞），每一張裡有：
賞別名稱、張數與籤數、**這一賞的買回價（一格）**、一行「抽到就能換 X 點 · 這一賞共承諾 Y 點」、
以及這一賞的卡片**橫向縮圖軌**。新挑進來的卡先落在「還沒分賞別」那一組，
多選之後一次指派。要調某一張的例外，點那張縮圖開貼底面板。

- 高度：**不隨張數成長**。12 張 1,538 px、30 張 1,538 px（原型實測）。
- 代價一：**卡片與它的最終金額不再同時全部可見**。要逐張核對得展開或點開。
  → 緩解：每一組固定顯示「這一賞共承諾 Y 點」與「其中 N 張單獨改過金額」，
  另外給一顆「展開成清單」把該賞別攤成垂直清單（展開 D 賞 23 張時整段回到 2,680 px ——
  這個代價是**使用者自己選的、而且只在那一個賞別上**）。
- 代價二：**橫向捲軸的可發現性與無障礙比垂直清單差**。
  → 緩解：軌道用 CSS scroll-snap（站上 `SnapRail.vue` 已經是這個做法，鍵盤 focus 會自動捲到位），
  並且永遠留「展開成清單」這條純垂直的路。
- 代價三：**要學一個新的心智模型**（先分組、再填錢），跟現在「挑完卡逐張填」不一樣。
  → 緩解：其實這才是賣家腦中原本的模型（見 4.1）。而且現況已經先猜好賞別了，
  照舊操作的人不會被強迫先分組。
- 代價四：實作量最大的一案（要新的分組元件、批次指派、貼底面板）。

### 方向三：表格化 ＋ 橫向捲（或虛擬捲動）

把手機版也做成真表格，表頭固定，整張表橫向捲；列高壓到 44 px，超過 20 列時虛擬捲動。

- 高度：30 張 ≈ 44×30 = 1,320 px；虛擬捲動可以壓到定值。
- 代價一：**393 px 上的橫向捲表格是已知的體驗地雷**：手指往下捲會誤觸橫向、
  表頭與內容容易脫鉤、螢幕閱讀器要在二維裡導航。
- 代價二：**154 個控制項一個都沒少**，只是排得整齊一點。「太亂」的主因沒被處理。
- 代價三：虛擬捲動會讓「跳到出問題的那一格」（`goTo()`）變難 ——
  那一列可能根本不在 DOM 裡，而這一頁剛修好的正是「按了沒反應」。**風險太高。**

### 方向四（補充）：只加批次編輯，版面不動

「A 賞全部設成 X」當成一顆按鈕加在現有表格上。

- 它確實砍掉重複勞動，但**一 px 都沒有縮短版面**。而使用者三個抱怨裡有兩個是版面。
- 它值得做，但它是方向二的一個零件，不是一個方向。

### 對照

| | 方向一 摘要行 | **方向二 賞別分組** | 方向三 表格橫捲 | 方向四 只做批次 |
|---|---|---|---|---|
| 30 張時的段高 | ~2,000 px | **1,538 px** | ~1,320 px | 7,457 px |
| 高度成長 | O(n) | **O(賞別數)，上限 6** | O(n) 或定值 | O(n) |
| 控制項數（30 張） | ~34 | **23** | 154 | 154 |
| 砍掉重複勞動 | 否 | **是** | 否 | 是 |
| 無障礙風險 | 低 | 中（橫向軌，有垂直退路） | **高** | 低 |
| 對 `goTo()` 錨點的衝擊 | 小 | 中（見 §8） | **大** | 無 |
| 實作量 | 中 | 大 | 中 | 小 |

## 4. 推薦：方向二

### 4.1 為什麼是它 —— 逐張填本來就是多餘的

`SellerNewPoolPage.vue` 的檔頭已經把答案寫在那裡了：

> 買回價**按賞別填**，一個賞別一個絕對金額 …… 同一個賞別裡的卡價值本來就相近 ——
> **那正是分賞別的意義**。某一張在該賞別裡特別貴的時候可以單獨覆寫，那是例外不是常態。

這條判斷是對的。但**版面沒有照著它做**：買回價按賞別填，可是每一列還是給了一個
買回價的框；賞別是這個池真正的結構，可是畫面上它只是每一列裡的一個下拉選單。

換句話說 —— 資料模型早就是「賞別 → 卡」，而畫面畫的是「卡 → 賞別」。
把畫面翻回資料模型的方向，那 154 個控制項有 130 個自己就消失了。

賣家腦裡的順序也是這個：「這場 A 賞放這張、B 賞兩張、剩下都丟 D」。
沒有人是想著「第 17 張卡的買回價是多少」。

### 4.2 實測

原型（`docs/proto/prize-editor.html`）左右兩具 393×852 的手機跑同一份資料，
數字是頁面自己即時量的：

| 卡片張數 | 1 | 5 | 12 | 30 |
|---|---:|---:|---:|---:|
| 段高　現況 → 提案 | 825 → 619 | 1,837 → 1,232 | 3,430 → **1,538** | 7,485 → **1,538** |
| 減少 | −25% | −33% | **−55%** | **−79%** |
| 控制項　現況 → 提案 | 6 → 2 | 28 → 10 | 64 → **19** | 154 → **23** |
| 這一段幾屏　現況 → 提案 | 1.0 → 0.7 | 2.2 → 1.4 | 4.0 → **1.8** | 8.8 → **1.8** |

原型左側是照著真頁面的 CSS 重做的複本，用來驗證它值得信：
段高在 5 / 12 / 30 張時分別是 1,837 / 3,430 / 7,485 px，
真頁面量到 1,844 / 3,412 / 7,457 px —— **誤差 0.4–0.5%**。

12 張與 30 張的段高完全相同（1,538 px），因為兩者用到的賞別數一樣。
**再加 18 張卡，版面一個 px 都沒長。**

### 4.3 提案的一列（一組）長什麼樣

```
┌─────────────────────────────────────────┐
│ ■ A 賞   1 張 · 1 籤        [展開成清單] │
│ 這一賞的買回價                            │
│ [ 4800                     ]  點 / 張    │  ← 44px
│ 抽到就能換 4,800 點 · 這一賞共承諾 4,800 點 │
│ [卡][卡][卡][卡][卡] →（橫向捲）           │  ← 縮圖 54px 寬
└─────────────────────────────────────────┘
```

點任一張縮圖 → 貼底面板（`.sheetWrap` / `.sheet`，抄 `MyCardsPage.vue` 那一套）：
卡片身分、賞別（六顆 44 px 的鈕）、籤數、這一張的買回價（placeholder 是賞別預設）、
參考價、移除。長按縮圖進多選，選好之後上方冒出「已選 N 張 · 設為 ▢ 賞」。

## 5. 說明怎麼寫才直接

### 5.1 賣家在那一格真正的問題

不是一個問題，是兩個，而且有先後：

1. **「填了會怎樣？」**（我得先知道這一格是什麼，才知道要不要在意）
2. **「我該填多少？」**（然後才是決策）

現在那段 103 字回答的是**第三個**問題：「這件事在系統裡是怎麼運作的」——
鎖死、雜湊、保留額、不需要基準。那些都是真的，但賣家在填第一格的當下不會問。

### 5.2 改寫

**前（103 字，4 句）：**

> 你答應照這個價把卡買回來的金額，**開賣前鎖死、開賣後改不了**（它被寫進公平性承諾的雜湊裡）。
> 玩家按下接受時，這筆錢直接從你這個池的保留額出。同一個賞別的卡價值本來就相近，
> 所以填一個絕對金額就好，**不需要任何基準**。

**後（72 字，3 句）：**

> **買回價一個賞別填一次**：填多少，抽到那一賞的人就能拿多少點跟你換走那張卡，
> 錢從這個池的池款出。填高比較好賣，但那是你真的要付的錢。**開賣後改不了。**

再加上每一組自己的一行（這一行是算出來的，不是文案）：

> 抽到就能換 **4,800** 點 · 這一賞共承諾 **4,800** 點

以及一個折疊：

> **為什麼買回價是一個絕對金額，不是比率？**
> 比率要有基準，而唯一的基準是你自己填的參考價 —— 那是循環論證：你把參考價填高，
> 回饋率就自己變漂亮。金額則是你真的要付出去的錢，填高等於承諾多賠，
> 所以這個數字不需要外部行情就是誠實的。
> **爆賞也要填**：爆賞發的是保底卡，那張卡一樣會被抽到、一樣可以換回點數。

### 5.3 為什麼那樣寫

- **第一句用具體的動作，不用定義。**「你答應照這個價把卡買回來的金額」是一個定義，
  讀者要自己把它演成一個畫面。「填多少，抽到那一賞的人就能拿多少點跟你換走那張卡」
  已經是那個畫面了。
- **第二句同時給兩個方向的後果。**「填高比較好賣，但那是你真的要付的錢」——
  這一句才是真正在幫他決定填多少。原文完全沒有這一句。
- **「不可逆」放最後，一句話。** 原文把它放第一句還加了括號解釋雜湊，
  結果是最重要的那半句（我該填多少）被擠到第四句去了。
- **「不需要任何基準」整句移進折疊。** 它在回答「為什麼不是比率」，而賣家還沒問。
  他要問的時候會自己點開；沒問的時候它是雜訊。
- **「保留額」換成「池款」。**「保留額」是系統詞彙，站上其他地方沒有教過它。
- **公平性雜湊那段不刪，搬家。** 它已經在右欄「公平性」卡片裡講了一次
  （「封存的內容包含每一張卡的卡號與版本與你宣告的買回價，你自己也無法在開賣後更動」）——
  同一件事講兩次，第二次就是雜訊。

### 5.4 那 114 字的 `.twoCols` 直接消失

它在解釋「參考價 ≠ 買回價」。提案裡這兩件事不再並排：
買回價在賞別組上（一個賞別一格），參考價在單卡面板裡，各自帶一行 20 字的說明：

- 買回價那格：「空著就照 A 賞的 4,800 點。只有這張在同一賞裡特別貴才要改。」
- 參考價那格：「只顯示給買家看，不構成承諾。空著就是『未標示』。」

**一段 114 字的說明，靠改版面拿掉，而不是靠改寫。** 這是這次最划算的一筆。

（`.pickNote` 那 99 字不動：它講的是「卡片身分會進公平性承諾」，是這一頁真正該教的事。）

## 6. 每一列現在有 8 樣東西，哪些可以拿掉

| 元素 | 每一張都要看到？ | 判斷 |
|---|---|---|
| 卡片縮圖 | **要** | 認卡最快的東西，而且是唯一一個「不用讀字」的。留，還放大（34 → 54 px）。 |
| 卡名 | **要** | 縮圖分不出同一隻寶可夢的不同卡。留在縮圖下方一行（10 px，截斷）。 |
| 卡號／系列 | 不要 | 只有在**兩張挑進來的卡同名**時才需要分辨。移進面板；同名衝突時才在縮圖下補一行。 |
| 鑑定編號 | 不要 | 開池當下不需要核對編號（後端會擋重複上架）。移進面板。縮圖上留一個小角標表示「這是鑑定卡」。 |
| 賞別下拉 | **要**，但不是每列一個 | 賞別就是分組本身 —— 卡在哪一組，賞別就是什麼。**每列一個下拉整個消失**（30 個 → 0 個）。 |
| 數量 | 例外才要 | 有鑑定編號的卡固定 1 籤（既有規則）；目錄卡才可能 >1。縮圖上有 `×3` 角標，改在面板裡改。 |
| 參考價 | **不要** | 它不參與任何計算、不構成承諾、只顯示給買家。給它一個常駐的框，等於讓它看起來跟買回價一樣重要 —— 那正是 114 字說明要去解釋的誤會。移進面板。 |
| 買回價覆寫 | **不要** | 依照這一頁自己的判斷，它是**例外**。常駐的空框讓例外看起來像常態。移進面板；有覆寫的卡在縮圖上有「改」角標，組層級顯示「其中 N 張單獨改過金額」。 |
| 刪除鈕 | 不要 | 移除本來就已經有另一條路（`CardPicker` 的已選清單）。面板裡一顆全寬的「從這個池移除」，比一顆 33 px 的叉安全也好按。 |

結果：**常態下每張卡的可見資訊 = 縮圖 + 卡名 + 角標；可見的可互動控制項 = 0**。
整段從 154 個控制項降到 23 個（6 個賞別買回價 + 分組的展開鈕 + 批次指派）。

## 7. 既有決定：哪些保留、哪些被我推翻

`SellerNewPoolPage.vue` 的註解記了很多「為什麼是現在這樣」。逐條交代。

### 7.1 完整保留（而且被加強）

| 既有決定 | 提案怎麼處理 |
|---|---|
| **買回價按賞別填，不是比率、不是每張一個** | 保留，並且變成畫面的**主結構**。現況是「模型按賞別、畫面按卡」，提案讓兩者一致。 |
| **爆賞也要有買回價** | 保留。爆賞跟其他賞別一樣是一個分組，用到就出現、就要填。折疊裡明寫理由。 |
| **逐項覆寫是例外不是常態** | 保留，並且**讓它真的長得像例外**（要點一下才看得到，有覆寫的卡才有角標）。 |
| **參考價選填、不參與計算、空著顯示「未標示」、不要退成 0** | 保留。只是換位置。 |
| **經濟護欄三個門檻（100 / 90 / 25）與 `computeEconomics` 單一來源** | 完全不動。提案把即時試算**往上搬到獎項配置區的頂端**（現況在右欄，900px 以下右欄掉到整頁最底），讓改買回價的當下就看得到比率動。 |
| **送出鈕不禁用、「還差什麼」清單、按了會跳到那一格** | 保留，見 §8 的錨點契約。 |
| **有鑑定編號的卡只能開 1 籤** | 保留規則。見下方 7.2 的一點修正。 |
| **範本複製時抽掉鑑定編號、標記 needsRepick** | 保留。需要重挑的卡在縮圖上是紅框，並排在「還沒分賞別」那一組的最前面。 |
| **PSA 卡號對不上時的「確認是同一張卡」勾選** | 保留，移進單卡面板（它本來就是例外中的例外）。 |
| **到期日不在這張表上** | 保留那一行說明。 |

### 7.2 我確實動到的三條（明講）

1. **「表格 + 手機藏表頭」這個呈現方式，我推翻。**
   推翻的不是任何一條業務規則，是版面模型。理由在 §2：藏表頭等於承認欄位失去定義，
   而失去定義的三個數字框正是「太亂」的來源。

2. **鑑定卡的數量欄，從「可以輸入、輸錯再報錯」改成「不給輸入」。**
   現況是 `<input min="1">` 加一條 `problems` 檢查（「有鑑定編號的卡只能開 1 籤」）。
   提案在面板裡直接畫成一格不可編輯的「1 籤（固定）」，底下一行講理由。
   **規則沒變，只是把它從「事後驗證」搬到「不可能輸錯」。**
   注意：`problems` 那條檢查**不能刪** —— 範本複製與後端回來的資料仍可能帶 `qty > 1`，
   它是最後一道網。

3. **「參考價」與「買回價覆寫」失去常駐位置。**
   兩者都是既有決定明講的「選填／例外」，所以嚴格說我沒有推翻決定，
   而是讓版面終於符合那個決定。但這確實改變了操作成本：
   **要逐張核對參考價的賣家，從「捲」變成「點」。** 這是我知道且接受的代價，
   緩解是組層級的「其中 N 張單獨改過金額」與「展開成清單」。

### 7.3 我沒有碰的

`FLOOR_MINT / FLOOR_THIN / FLOOR_PREDATORY`、`BUYBACK_MIN / MAX`、
`computeEconomics` 的分子定義、manifest v4 送出的是**解析後的絕對金額**而不是規則、
玩法只開放 muteki、`CardPicker` 的 60 張上限 —— 全部照舊。

## 8. 跟「按了沒反應」那條工作線的介面

那條線正在修的是 `problems` / `goTo()` / 送出鈕的回饋。這個提案會動到**錨點的形狀**，
兩邊要對一次，否則會再長出一條「按了沒反應」的死路：

| 現在的錨點 | 現在指向 | 改版後應該指向 |
|---|---|---|
| `f-tierbuy` | 買回價區塊（整塊） | **出問題的那一個賞別組**（`f-tier-A`…），並 focus 那一格 |
| `f-prizes` | 獎項表的第一個節點 | 獎項配置區段（仍要存在，而且**不能是 `v-if` 掉的空 div**） |
| 數量／鑑定卡的問題 | `f-prizes`（只捲到表頭） | 應該**捲到該卡所在的組，並打開那張卡的面板** |

三條硬性要求：

1. **每一個 `Problem` 都要跳得到一個看得見的東西。** 分組摺疊之後，
   問題的目標可能藏在收起來的組裡 —— 跳過去之前要先把那一組展開。
2. **`goTo()` 找不到節點時仍然要出聲**（現況的 `jumpMiss` 保留）。
3. **錯誤要在組層級也看得見**：某個賞別的買回價不合法時，那一組要有紅框，
   不能只靠底下的清單講。

建議把 `Problem` 從 `{ anchor, msg }` 擴成 `{ anchor, msg, tier?, cardKey? }`，
由 `goTo()` 負責「展開該組 / 打開該卡的面板」再捲動。

## 10. 原型怎麼用

`docs/proto/prize-editor.html` —— 直接用瀏覽器打開，不需要伺服器、不連外、無 emoji。

- 上方切 **1 / 5 / 12 / 30** 張，兩具 393×852 的手機同時重畫；看板上的四個數字是即時量的。
- 「再挑 5 張（未分賞別）」→ 右邊冒出「還沒分賞別」那一組 → 按「全部設為 C 賞」看批次指派。
- **長按**任一張縮圖進多選，選幾張之後用上方的「設為 ▢ 賞」一次改掉。
- **點**任一張縮圖開貼底面板：改賞別、改籤數（鑑定卡是鎖住的）、單獨改買回價、改參考價、移除。
- 改任何一格買回價，上方的保底回饋率會跟著動（門檻用的是 `src/shared/economics.ts` 的
  100 / 90 / 25）。
- 右上角可以切深色／淺色，兩套色票都抄自 `src/styles/tokens.css`。
- 提案側所有可觸控目標實測 **≥ 44 px**（原型裡跑過檢查，回傳空陣列）。

原型是**設計稿，不是要合併的程式碼**：它用字串模板重畫整塊，不是 Vue，
真的實作要照 §9 第 3 步走。
