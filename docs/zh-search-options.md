# 中文（繁體）卡名搜尋：方案評估

> 狀態：只研究、未實作。資料實測日期 2026-09-15。
> 實測數字來自對 api.tcgdex.net 與 PokeAPI 的公開請求，不是推測。

## 一句話結論

**推薦方案 B：預先產生一份「日文卡名 ↔ 繁中卡名」對照表**（來源是 TCGdex 的 zh-tw 目錄 ＋ PokeAPI 的寶可夢繁中名），
前端挑卡與後端卡冊搜尋共用同一份表，把使用者打的中文先換成日文卡名再走現有搜尋。
朱紫（SV）與劍盾（S）世代可覆蓋約 97～99% 的日版卡，MEGA（M）世代約 89%，工作量「中」。

---

## 一、現況（讀程式的結果）

### (a) 卡冊搜尋

- 位置：`server/src/routes/prizes.ts` 約 286～310 行。
- 做法：`q` 包成 `%q%`，對 `p.card->>'name'`、鑑定編號、`p.card->>'setCode'` 三欄做 `ilike`。
- 卡名存的是**當初寫進去的那個字串**：
  - 從目錄挑的卡：`src/lib/card-pick.ts` 直接用 TCGdex 日文名（例如「リザードンex」）→ 打中文搜不到。
  - 種子資料／手打的卡：本來就是中文（`server/src/seed.ts` 的「噴火龍 ex SAR」）→ 打中文搜得到，打日文反而搜不到。
  - 所以現在是**混合語系**，中文搜尋其實「有時會中」，更容易讓人困惑。
- 限制：`card.name` 是公平性 manifest 的一部分（`src/shared/fairness.ts`），也在公開白名單（`server/src/card-public.ts`）。
  **不能為了搜尋去改寫 `name`**，中文名只能放在旁邊（另一張表或另一個欄位）。

### (b) 上傳／開池時挑卡的搜尋

- 元件：`src/components/CardPicker.vue`（`SellerNewPoolPage.vue` 使用），呼叫 `src/lib/tcgdex-catalog.ts` 的 `searchCards()`。
- 外部 API：只打 TCGdex，前端直接 fetch，沒有經過自家後端。
  - 主要端點 `https://api.tcgdex.net/v2/ja`；英文繞路時才打 `/v2/en`。
- 搜尋是一條「依序往下掉」的路：卡號/總數 → 套牌代號＋編號 → 純編號 → 套牌代號 → 英文寶可夢名（繞 dexId）→ 日文卡名。
- **沒有中文這一段**。中文字串最後會掉到日文 `?name=`，必然 0 筆。

### (c) 卡片資料裡的 dexId

- `CardItem`（`src/shared/domain.ts`）與 `prizes.card` jsonb **沒有 dexId 欄位**，只有 `artId`（例如 SV4a-349）、`setCode`、`cardNo`、`name`。
- 能取得 dexId 的地方只有 TCGdex：`/v2/{lang}/cards/{id}` 詳情有 `dexId` 陣列、`/cards?dexId=eq:25` 可反查。
  實測 SV4a-349 的詳情 `dexId` 是空的，資料並不齊，靠 dexId 當唯一橋接不可靠。
- 現有英文繞路（`dexIdFromEnglish`）已經證明 dexId 橋接能跑，但它**只能找到「同一隻寶可夢」，不是「同一張卡」**，而且訓練家／物品／能量卡完全沒有 dexId。

## 二、資料來源實測

### 1. TCGdex zh-tw（最關鍵的發現）

- `/v2/zh-tw/sets` 有 98 套，`/v2/zh-cn/sets` 有 57 套（簡中以中國大陸版 CS 系列為主）。
- **zh-tw 的套牌代號與日版完全同一套命名**：SV4a、SV2a、SV8a…… 98 套裡有 62 套跟 `/v2/ja` 的 id 一模一樣。
  `/v2/zh-tw/cards/SV4a-349` → 「噴火龍ex」，`/v2/ja/cards/SV4a-349` → 「リザードンex」。
- 名稱搜尋可用：`?name=噴火龍` 26 筆、`奇樹` 14 筆、`派帕` 14 筆、`大師球` 2 筆、`博士的研究` 42 筆。訓練家卡也有。
- 全量：zh-tw 7,436 張、ja 12,781 張，同 id 兩邊都有的 3,959 張。整包清單 `/v2/zh-tw/cards` 約 520 KB，CORS 開放。
- 缺口：
  - **zh-tw 沒有卡圖**（`image` 為空），只能拿名字，圖仍要用 ja 的。
  - **高編號的密卡多半沒有**：例如 SV8 缺 107～138、SV10 缺 99～132、SV4a 缺 355～360。偏偏 SAR/UR 正是平台主力商品。
    但密卡的卡名跟同套普卡相同（スコヴィランex 的 SAR 與普卡同名），所以「用卡名對卡名」就補得回來。
  - **沒有 MEGA（M1S、M1L、M2…）與 SV11B/SV11W**，zh-tw 資料停在 SV10 左右。
  - 少量 id 對錯位：日文名對到多個中文名的有 63 組（例如 ヒトカゲ 對到「小火龍」6 次、「墨海馬」1 次），取多數即可。
- 授權：TCGdex 資料庫 MIT 授權、允許商用；但寶可夢名稱與卡圖的權利仍屬寶可夢公司。zh-tw 內容來源未標明，可能也是從官方網站整理。

### 2. 寶可夢官方台灣卡牌網站（asia.pokemon-card.com/tw）

- 有卡片搜尋與詳情頁（例如 `/tw/card-search/detail/16705/`），資料最新、含 MEGA 世代與訓練家卡。
- 但它**用的是台灣版的套牌與編號**（例如 MC 系列的 234/742），跟日版 artId 不能直接對。
- 條款（`/tw/policy/`）：禁止複製、轉載、散布站上內容，也禁止把服務用於營利目的；未明文提到爬蟲。
  VaultDraw 是營利平台，**抓它的資料建表有明顯授權風險，不建議**。只適合人工查證單一譯名。

### 3. PokeAPI（寶可夢物種名）

- `pokemon-species` 的 `names` 有 `zh-hant`、`zh-hans`、`ja-hrkt`、`ja`。例：6 = リザードン / 噴火龍；1025 = モモワロウ / 桃歹郎。
- 1,025 種全部有繁中名。GraphQL 端點 `graphql.pokeapi.co/v1beta2` 一次撈完全部名字（約 160 KB）。
- **不需要 dexId 當中介**：直接得到「日文寶可夢名 → 繁中名」，比 dexId 橋接少一跳。
- `item` 也有繁中名（例如 master-ball → 大師球），但那是遊戲道具，跟卡牌物品卡只有部分重疊。
- 沒有訓練家人物名（奇樹、派帕、莉莉艾）。
- 授權：PokeAPI 資料開放免費使用；寶可夢名稱屬寶可夢公司商標，但作為搜尋用的名稱對照，風險低。

### 4. 訓練家／物品卡的中文名從哪來

| 來源 | 覆蓋 | 風險 |
| --- | --- | --- |
| TCGdex zh-tw | SV、S 世代的訓練家卡大致都有（奇樹、派帕、博士的研究） | 低（MIT） |
| PokeAPI item | 只有跟遊戲道具同名的（大師球、力量頭帶這類） | 低 |
| 官方台灣網站 | 最完整、含 MEGA 世代 | 高（條款禁止複製與營利使用） |
| 人工補表 | MEGA 世代新出現的熱門訓練家（莉莉艾的決心、光、阿塞蘿拉…），幾十到一兩百筆 | 低（自己輸入的對照，數量小） |

## 三、覆蓋率模擬

用實際下載的全量清單模擬「日版卡的日文名能不能換到中文名」（以卡片張數計）：

| 世代（ja 張數） | 只用 TCGdex zh-tw 對照 | ＋PokeAPI 寶可夢名 |
| --- | --- | --- |
| 朱紫 SV（3,677） | 96% | **98%** |
| 劍盾 S（1,796） | 99% | **99%** |
| MEGA M（1,924） | 71% | **89%** |
| 太陽月亮 SM（3,139） | 53% | 76% |
| 更舊（2,245） | 14% | 22% |

- PokeAPI 那一欄的做法：去掉「メガ」「〇〇の」「ex / V / VMAX / GX」等前後綴後，比對物種日文名。
- MEGA 剩下的缺口幾乎全是新訓練家、新物品、新能量卡（見上表人工補表）。
- 平台主力是 SV 與 MEGA 世代的高價卡，實際影響面比「全目錄」數字小很多。

## 四、方案比較

### 方案 A：執行時直接打 TCGdex zh-tw（不建表）

- 做法：`searchCards()` 加一段「字串含漢字 → `/v2/zh-tw/cards?name=q`」。
  拿到 id 後，同 id 的日版卡直接顯示（圖用 ja）；再取幾個代表 id 的日文名回頭查 `/v2/ja/cards?name=`，把密卡補回來。
- 覆蓋：SV、S 可用；**MEGA 世代 0**（zh-tw 沒有那些套）；寶可夢卡與訓練家卡同等。
- 改動：只有 `src/lib/tcgdex-catalog.ts`（＋`CardPicker.vue` 提示文案）。
- **卡冊搜尋幫不上**：後端不能每次搜尋都去打外部 API。
- 請求數：每次 1 ＋ 2k 個（k = 不同卡名數，需設上限），比現在慢。
- 授權風險：低。工作量：**小**。

### 方案 B：預先產生對照表（推薦）

- 做法：
  1. 寫一支產生腳本：下載 zh-tw 與 ja 全量清單，依同 id 配對出「日文名 → 繁中名」（多數決去雜訊），
     再合併 PokeAPI 的物種名，最後合併一小份人工補表。輸出 JSON（估計 3,000 組上下、壓縮後數十 KB）。
  2. 挑卡（前端）：中文輸入 → 在表裡找「中文名包含 q」的日文名（可能多個）→ 用現有 ja `?name=` 查（設上限）。
  3. 卡冊（後端）：同一份表放進 server，`q` 含漢字時展開成日文名陣列，
     SQL 多一段 `p.card->>'name' ilike any(...)`；原本的中文 ilike 保留（手打的中文名照樣中）。
  4. 簡體輸入：可選配繁簡轉換（或把 zh-hans 名也放進表）。
- 覆蓋：SV 98%、S 99%、M 89%、SM 76%；寶可夢卡最好，MEGA 訓練家靠人工補表。
- 改動檔案：
  - 新增：產生腳本（例如 `scripts/build-zh-names.ts`）、共用對照表（例如 `src/shared/card-names-zh.json`）、人工補表。
  - 修改：`src/lib/tcgdex-catalog.ts`（多一個 `name-zh` 搜尋欄位）、`src/components/CardPicker.vue`（提示照實說「以卡名對照找到」）、
    `server/src/routes/prizes.ts`（q 展開）。
  - **不動** `card.name`、manifest、公開白名單，不需要資料庫 migration（表放在程式碼裡）。
- 資料要預先建表：要，新系列發售後重跑腳本。
- 授權風險：低（TCGdex MIT ＋ PokeAPI 開放資料 ＋ 自己的補表）。工作量：**中**（約 2～3 天含測試）。

### 方案 C：以官方台灣網站為資料來源

- 做法：爬 asia.pokemon-card.com/tw 的卡片資料庫建表，再想辦法把台灣版編號對回日版 artId。
- 覆蓋：理論上最高，含 MEGA 世代的訓練家卡。
- 問題：條款禁止複製與營利使用；台版與日版編號不同，對回 artId 本身就是一個大工程；網站改版就壞。
- 授權風險：**高**。工作量：**大**。不建議。

### 附帶：dexId 橋接要不要做？

不必另外做。方案 B 直接用「日文名 ↔ 中文名」，不需要經過 dexId；
而 dexId 在卡片資料裡沒有、TCGdex 詳情也常是空的，訓練家卡更沒有。現有的英文 dexId 繞路可以保留，不衝突。

| | A 執行時 zh-tw | **B 預建對照表** | C 官方網站 |
| --- | --- | --- | --- |
| 挑卡搜尋 | 可 | 可 | 可 |
| 卡冊搜尋 | 不可 | 可 | 可 |
| SV / S 覆蓋 | 高 | 高（98～99%） | 高 |
| MEGA 覆蓋 | 無 | 89%＋人工補 | 高 |
| 訓練家卡 | SV/S 有 | SV/S 有、MEGA 靠人工補 | 有 |
| 預先建表 | 否 | 是 | 是 |
| 授權風險 | 低 | 低 | 高 |
| 工作量 | 小 | 中 | 大 |

## 五、推薦與第一步

**推薦方案 B**：一份表同時解決挑卡與卡冊兩處，不動公平性承諾的欄位，授權乾淨，主力世代覆蓋率接近全滿。

**第一步**：先只寫產生腳本，輸出對照表與一份覆蓋率報告（每個世代命中率、多義名清單、MEGA 未命中前 100 名），
不接任何畫面。看完報告再決定人工補表要補多少，然後才接 `searchCards()`（前端）、最後接卡冊 SQL（後端）。

注意事項（實作時）：

- 中文名比對要先正規化：去掉 `< >` 與全形括號、`ex` 前的空白、全半形差異（TCGdex 中文名是「<派帕的>原野水母」這種寫法）。
- 一個中文字串可能對到很多日文名（打「皮卡丘」會中「皮卡丘ex」「〇〇的皮卡丘」），前端要設上限並照實顯示「以卡名對照找到」。
- 多義名（同一日文名對到兩個中文名）取出現次數最多的，並在報告裡列出來人工確認。
- 表要記錄產生日期與來源版本，新系列發售後重跑。
