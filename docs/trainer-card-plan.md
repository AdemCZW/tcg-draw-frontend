### 0.2 但「角色」是一個沒有臉的假人

實測。看原生解析度的成品才看得出來：佔位樣板的角色**沒有五官** ——
瀏海底下兩顆深色圓點當眼睛，沒有鼻子、沒有嘴、沒有臉部輪廓線。

這件事的後果比「醜」嚴重：

- **換臉品質現在完全無法評估。** 沒有臉可以換，也沒有基準可以比。
- **構圖的關鍵比例現在也無法評估。** 臉在畫面裡佔多大、頭有沒有被上緣切到、
  換臉模型看得到的臉部像素夠不夠 —— 這些都要等真樣板才知道。
  規格 §6.2 說半身構圖「臉部佔比也更大使換臉品質更穩」，那是規格的宣稱（待查），
  不是這個 repo 驗過的東西。

**推論**：所以「生成並核准正式樣板」不只是第二階段的第一件事，它是**唯一**
可以解鎖其他判斷的那件事。在它之前討論「要不要多做幾張樣板」是在猜。

### 0.3 新發現：成品頁的主要按鈕被底部導覽的寶貝球蓋住

**實測，這一輪新發現的，第一階段的 commit 訊息沒有提到，repo 的 e2e 也抓不到。**

在 375×812、使用者**剛做完卡片落地的那個捲動位置（scrollY = 0）**：

```
儲存到相簿 按鈕     x=16..359   y=716..764   中心點 (188, 740)
底部導覽 nav.bnav   y=755..812  h=57  z-index 60
中央凸起的寶貝球     x=160..216  y=734..762   ← 比導覽列頂端還高 21px
```

`document.elementFromPoint(188, 740)` 回傳的是 **`rect.pb-top`** ——
寶貝球的上半部，不是那個按鈕。

橫向掃描按鈕中線（實測，dy 為相對按鈕中心的偏移）：

```
dy = -20, -12   整條都打得到按鈕
dy =  -4 … +12  中間 x±20 的那一段打到 rect.pb-top（寶貝球）
dy = +20        整條都打到導覽列（A.item / circle.pb-btn）
```

也就是說：**「儲存到相簿」正中央約 56px 寬的那一塊是死區，點下去會跳到「抽選」頁。**

捲動一格（scrollY ≥ 20）之後就正常了。所以這不是「永遠壞」，是
**「使用者落地當下的那一幀壞」** —— 而那正是他最可能直接伸手去按的時刻。

為什麼這條特別嚴重，而不是一般的版面瑕疵：

- 規格 §5 C-3 明訂成品只在記憶體裡，**離開頁面就無法復原**
- 誤觸的結果是「跳到抽選頁」＝ 離開頁面 ＝ 剛做好的卡永久消失
- 使用者不會知道發生什麼事，他只會覺得「按了儲存結果 App 亂跳，圖不見了」

**為什麼 repo 的 e2e 沒抓到**（讀碼）：`e2e.mjs` 檢查的是觸控目標的**尺寸**
（≥44px），沒有檢查**遮擋**。而 Playwright 的 `.click()` 會自動捲動到可點擊
位置再點，所以它永遠不會重現使用者的落地狀態。

修法與優先度見第七節 T-0；驗收要加的檢查見第八節 S-0。

### 0.4 資產管線的真相跟規格寫的不一樣（這件事讓「多樣板」變便宜）

**讀碼 + 實測。** 規格 §6.2 列了四個資產並說「這四個檔一起定案、一起鎖死，
更換樣板 = 四個檔全部重做」，讀起來像四份手工。實際上不是。

規格說的四個檔 vs 現在真正存在的四個檔：

| 規格 §6.2 | 實際 `src/features/trainer-card/assets/` | 差異 |
|---|---|---|
| `template.jpg` | `template.jpg`（86,533 B） | 一樣 |
| `finger-mask.png` | `finger-mask.png`（11,296 B） | 一樣 |
| `coords.json` | `coords.json`（811 B） | 一樣 |
| `frame.png` | **不存在** | 外框是程式畫的，見 T-2 |
| —— | `card-shading.png`（40,242 B） | 規格沒有的第四個檔（陰影層） |

而且後三個**不是手做的，是一支腳本從 template.jpg 算出來的**
（[`scripts/trainer-card/measure_template.py`](../scripts/trainer-card/measure_template.py)
第 314 / 328 / 348 行分別寫出 finger-mask.png、card-shading.png、coords.json）。

**所以換樣板的實際流程是：把新的 template.jpg 放進 assets/，跑一次
`python scripts/trainer-card/measure_template.py`。** 不是四份手工。

但**有一個真正的成本，而且它不在規格裡**（讀碼）：那支腳本用的是寫死的門檻 ——

```python
card = region & (chroma < 24) & (mn > 125)      # measure_template.py:250
```

「彩度 < 24 且最暗通道 > 125 的中性色像素 = 白卡」。這組門檻是對著**佔位樣板**
調出來的，而佔位樣板是程式畫的純色圖。**真的 AI 生成圖會有 JPEG 雜訊、
環境光染色、邊緣輪廓線、可能還有色溫偏移。**

**推論**：每一張新樣板都可能要重調門檻並目視確認遮罩與陰影。這才是「多一張
樣板」的真實成本 —— 不是那次 20 秒的付費呼叫，是那次調參與驗收。
我沒有辦法在沒有真樣板的情況下估這件事要多久（待查）。

另外一個結構限制（讀碼）：腳本只認固定路徑 `assets/template.jpg`，
`compose.ts` 也是靜態 import 單一份 `COORDS`。**要支援 N 張樣板需要先把這一層
改成可定址的**，那是小改動，但不是零改動。每張樣板的資產大小約
86 + 40 + 11 KB ≈ **138 KB**（實測 `ls`），都在 lazy-load 的 chunk 裡。

## 二、樣板

### 2.1 生成與核准的流程

規格 §12 說要「反覆數輪，每次約 20 秒且為付費呼叫」，但沒有說**誰看、看什麼、
什麼叫過**。沒有驗收標準的「反覆數輪」會變成無限輪。

建議的流程（每一輪）：

1. 用規格 §6.2 的 prompt（**含那段必須追加的「no circular badges…」排除條件**，
   規格明講實測會自己長出類寶貝球徽章）生成 1 張，2K
2. **先跑機器驗收** —— 把新圖丟進 `measure_template.py`，它會印三個數字
   （腳本第 352–355 行，讀碼）：
   - `measuredRatio` —— 白卡比例，**必須落在 0.716 ± 0.02**（規格 §4.3 說
     實測是 0.725，誤差約 1px 不需修正）
   - `finger coverage` —— 手指佔卡片區域的百分比，**規格 §4.3 說健康值是 4.5%**。
     太低＝沒拿住卡（構圖假），太高＝手指蓋掉太多卡面
   - `shading range` —— 陰影層的明度範圍。**全部是 1.000 代表卡是全平的**，
     那張樣板貼上去的卡會浮在角色前面
3. **再做人眼驗收**（機器過了才做，省時間）：
   - 卡是**完全空白的純白矩形**（有任何印刷、邊框、文字就重來）
   - 沒有真實寶可夢的名稱／造型／招式、沒有商標、**沒有紅白圓形徽章或球體
     圖示**、沒有任何文字與數字（規格 §5 C-4，這是硬約束）
   - 角色沒有戴白手套（規格 §6.2 明說遮罩原理會失效）
   - 頭沒有被上緣切到、臉夠大
4. 過了就把 `template.jpg` 換掉、跑腳本、**把 `coords.json` 的
   `"_placeholder": true` 拿掉**，然後重跑 `e2e.mjs`

**誰驗收**：機器驗收（第 2 步）誰跑都行；**人眼驗收（第 3 步）必須是你**。
C-4 那幾條是法律風險，不是美感偏好，我不該代替你判斷「這個徽章算不算像寶貝球」。

**開發期用 0.5K**（規格 §7.3 建議，成本約 1/2），**只有最後定案那一張用 2K**。

### 2.2 一張樣板夠不夠 —— 我的判斷

規格的立場（§4.2）：構圖固定是**優點**，「示意圖 = 實際產出」。
你的顧慮：分享到社群時每張都長得一樣。

**兩邊都對，但它們講的不是同一件事。**

- 規格講的是**可預測性** —— 使用者按下去之前就知道會拿到什麼。那個價值跟
  樣板有幾張無關，只要每一張都先給看過就成立。
- 你講的是**辨識度衰減** —— 第 50 個人分享同一個構圖時，它就不再是新鮮事。

我的建議是 **先 1 張上線，但現在就把資產層做成可定址的**，理由有三個，
其中第三個我認為是決定性的：

1. **多樣板的成本不是線性的，但省下來的也不是第一張。** 第一張要付的是
   「prompt 調到能用」＋「量測門檻對真 AI 圖適不適用」（見 0.4）。
   第二張之後大多只剩調參。所以「先做一張」不會讓第二張變貴。
2. **辨識度衰減要有量才會發生。** 平台抽成 0%、金流未接通（見 §4.1），
   現在還沒有那個量。為一個還沒發生的問題先付四倍的樣板成本，順序是反的。
3. **使用者真正想炫耀的是自己的卡，不是角色。** 成品裡佔畫面 32%×30% 的
   那一塊（規格 §4.3）已經每個人都不一樣。角色是舞台，卡才是主角 ——
   **要增加成品的差異度，加樣板是最貴的做法，而且加在不重要的那一半。**

**如果你要 D-2 選多張**，那我建議的軸是**性別呈現**（一男向一女向的中性角色）
而不是風格或背景 —— 那是使用者最會因為「這不像我」而不分享的一個維度。
兩張的增量成本：多一輪生成與核准、多一次門檻調參、+138 KB chunk、
`compose.ts` 與 P4 多一個選樣板的畫面。

### 2.3 換樣板時要跑的流程（給未來的自己）

```
1. 新的 template.jpg 放進 src/features/trainer-card/assets/
2. python scripts/trainer-card/measure_template.py
   → 重新產生 finger-mask.png / card-shading.png / coords.json
3. 讀腳本印出的三個數字，照 2.1 第 2 步的門檻判斷
```

不是記憶體（檔頭第 9–12 行說明：Railway 重新部署會清掉記憶體，多副本會讓

## 四、成本與商業模式

**規格完全沒有這一節。** 這是我認為第二階段最該先想清楚的一塊。

### 4.1 先講一個會改變整個結論的事實

**讀碼，兩件事一起看：**

- **平台抽成目前是 0%** —— `docs/rules.md` 第十節，原文就三個字：「目前 **0%**」
- **金流還沒接通** —— `server/src/routes/admin.ts:54` 的註解說目前沒有接任何
  金流，點數是平台後台發的；`PrivacyPage.vue` 的 `topups` 欄位說明也寫
  「目前金流尚未接通」

合起來：**這個平台現在沒有任何一條收到錢的路徑。**

這件事對三個問題有直接後果：

1. **「引流」不成立。** 引流的意思是把新客帶進來，讓他日後產生收入。
   抽成 0% 且金流未通的情況下，一個新客帶進來的期望收入是 **NT$0**。
   所以「一個新客值不值 NT$13」這個問題，**在今天的參數下答案是「不值」——
   而且不是因為 13 太貴，是因為分母是零。** 這是 D-1 的依據。
2. **「收點數」回收不到現金。** 點數目前是後台發的，不是賣的。
   跟使用者收 30 點，平台的銀行帳戶不會多 30 元。
   **所以收點數是配給（rationing），不是收入（revenue）。**
   這不代表不該收 —— 配給本身有價值（見 4.3）—— 但**內部不可以把它記成收入**，
   那會讓之後所有的成本決策建立在假的數字上。
3. **每日硬上限是唯一真的防線。** 沒有收入對應的支出必須有天花板，
   而且是**絕對值的天花板**，不是「每人幾次」的相對上限。見 D-6。

### 4.3 我建議的守門設計

四層，由外而內。**每一層擋的東西不一樣，缺一層就有一個洞：**

| 層 | 機制 | 擋什麼 | 為什麼需要 |
|---|---|---|---|
| 1 | **Google Cloud 每日預算上限** | 帳單失控 | 規格 §9 第一層。唯一在我們的程式全部失效時還有效的一層 |
| 2 | **全站每日上游呼叫硬上限**（建議 200／日） | 一夜之間被打爆 | 一個 Postgres 計數器。**這是我最想加的一層，規格沒有** |
| 3 | **強制登入 + 每人每日上限**（建議 1 次／日） | 同一個人重複刷 | 見 D-4 |
| 4 | 每 session 3 次生成 / 4 次上游 | 單次 session 失控 | **已經做好了**（`GenerationBudget`，讀碼） |

**為什麼第 3 層要靠登入而不是 IP**（推論，但理由具體）：
台灣的行動網路是 CGNAT，同一個 IP 後面可能有幾百個真實使用者，
而同一個使用者切換 Wi-Fi／行動網路就換一個 IP。
**IP 限流在這個情境下同時誤傷真人又擋不住有心人。**
`rate-limit.ts` 既有的 bucket 也是這個思路 —— `card-upload-user:` 與
`card-upload-ip:` 兩個一起用，user 那條是主防線（40／15 分鐘），
IP 那條放寬（120／15 分鐘）只當兜底。**照抄那個形狀就好。**

**點數（D-5）**：建議 **30 點／次**，在使用者按下「開始生成」時扣，失敗退還。
30 點的理由：
- 站上票價的量級是 300 點（`ai-opportunities.md:126` 引的例子），30 點是
  「一次抽卡的十分之一」，直覺上是「小東西」而不是「另一個消費決策」
- 成本是 NT$5–13，30 點（名目 NT$30）在名目上覆蓋得過去
- **但要記得 4.1 第 2 點：這是配給不是收入。** 它的真正作用是讓使用者
  自己不會亂點，而不是把錢賺回來

### 4.4 一個新客值不值 NT$13 —— 我的判斷

**在今天的參數下：不值，因為期望收入是 0（見 4.1）。**

但這個答案有條件，而條件是可以改變的。**如果金流接通、抽成不是 0%**，
同樣的問題就變成一個正常的 CAC 計算：

```
新客期望價值 = 首年下單金額 × 抽成率 × 留存率
```

用一個保守的例子（**推論，全部是假設，我沒有這個平台的真實留存資料**）：
若一個新客首年抽 3 次、每次 300 點、抽成 5%，
期望價值 = 900 × 5% = **NT$45**，扣掉留存打折仍高於 NT$13。
**在那個世界裡，NT$13 的 CAC 是划算的**，而且划算得相當明顯。

所以我的判斷是：

- **今天**：把它當留存／好玩的功能，關在登入後面，設死每日上限。不推廣。
- **金流接通且抽成 > 0 之後**：這個功能才有資格被當引流工具，
  那時候再談要不要開放未登入試用、要不要買廣告。

**這個判斷可以被一個數字推翻**：如果你有「站上使用者的實際首年消費」的資料，
拿出來算一次就能取代我上面整段推論。我沒有那個資料（待查）。

現有的 [`src/pages/PrivacyPage.vue`](../src/pages/PrivacyPage.vue) 的體例（讀碼）：

一張表帶「方向」欄位（是我們送出去、還是你的瀏覽器直接連過去）、
最後有一張**依據表**把每一條主張對應到 `檔案:行號`。

新功能要補的東西必須照這個體例走。

### 5.0 先更正一個很多人（包括我一開始）會弄反的前提

**自拍在台灣個資法下不是「特種個資」。** 這跟直覺相反，而且它會改變要做的事。

個資法第 6 條第 1 項的特種個資是**窮舉**的六類：

> 「**病歷、醫療、基因、性生活、健康檢查及犯罪前科**之個人資料」

來源：https://law.moj.gov.tw/LawClass/LawSingle.aspx?pcode=I0050021&flno=6（查核日 2026-09-04）

**臉部影像、指紋、虹膜都不在裡面。** 個資會有一則論及虹膜的函釋，說生物特徵
「雖非屬個資法第 6 條第 1 項所列之特種個人資料，但…仍受個資法有關**一般個人資料**
…之規範」。
⚠️ **這則函釋我沒有取到逐字原文**（頁面 https://www.pdpc.gov.tw/News_Content/101/393/
抓下來只有導覽列，字號與日期查不到）。**要引用進法律文件之前請自行複查。**

**所以實務上的門檻是（推論，基於上面的條文原文）：**

| 要件 | 依據 | 對我們的意思 |
|---|---|---|
| 特定目的內、必要範圍 | 第 19 條 | 「做一張訓練家卡」就是那個特定目的，用完即丟正好符合必要範圍 |
| **告知義務** | 第 8 條 | **這是主要義務。** 蒐集目的、類別、利用期間／地區／對象／方式、當事人權利，都要講。這正好是 `PrivacyPage.vue` 檔頭第 6–8 行說的那個骨架 |
| 當事人同意 | 第 19 條 | P1 的勾選同意即可，**不需要第 6 條那種書面同意** |

**結論：不需要為了「生物特徵」另外做一套更嚴的流程。**
真正要做對的是**告知**（§5.1），而那本來就是這一頁的體例。

**兩件相關、時效性的事：**

- **跨境傳輸是允許的。** 第 21 條採「原則自由、例外限制」——
  主管機關「**得**限制之」，也就是沒有下限制令就可以傳。**跟 GDPR 方向相反。**
  來源：https://law.moj.gov.tw/LawClass/LawSingle.aspx?pcode=I0050021&flno=21（查核日 2026-09-04）。
  ⚠️ 目前有沒有對特定國家的現行限制令，**這一輪查不到**。
- **個資法修正案已於 2025-11-11 公布，但施行日由行政院另定，查核日尚未施行。**
  新增的是**個資事故通報義務**與主管機關的**行政檢查權**。
  來源：https://www.pdpc.gov.tw/News_Content/20/1010/（查核日 2026-09-04）。
  **推論**：這一條跟訓練家卡關係不大（我們不存圖，沒有可外洩的池），
  但它對整個站有影響，值得另案處理。

### 5.2 第三人肖像 —— 有人上傳別人的臉

**先講我不建議做的**：人臉比對、活體偵測、「這是不是你本人」的驗證。
理由不是做不出來，是**做了會更糟**：

- 站上沒有使用者的基準人臉可以比對（沒有實名照片），所以「是不是本人」
  在技術上就無從判斷
- 做一個看起來像在管、實際上管不到的機制，會讓平台從「我們有告知」
  變成「我們宣稱會擋但沒擋住」。**後者的責任比前者重。**

**建議做的，是一句具體、可執行、而且我們真的做得到的聲明**，放在 P1 同意書：

> 請只上傳你自己的臉。上傳他人照片需要事先取得對方同意；
> 若他人向我們反映，我們會配合處理。

三個部分各有作用：第一句是規範，第二句把責任明確放在上傳者，
第三句是我們真的做得到的承諾（因為成品不存在我們這裡，
「處理」實際上就是回應與必要時停權，這是做得到的）。

**同意書上不要寫「我們會審核」之類做不到的話。**

### 5.3 未成年人

現況（讀碼）：

- `PrivacyPage.vue` 已經有第八節「未成年人」，也已經有
  「法定代理人若發現未成年人未經同意使用本站…」的處理條款
- `users.birthday` 欄位存在，但 **PrivacyPage 第 68 行自己寫了「全部選填，
  註冊時不會逼你填」**，而說明裡寫「條款寫明未滿 18 歲須監護人同意，
  這是那一條的依據」

也就是說：**站上已經有 18 歲的規範，但沒有、也不打算有硬性的年齡閘。**

**我的建議是維持現狀，只在同意書加一句**，理由：

1. **一致性。** 抽卡本身（金額更大、法律風險更高）都沒有年齡閘，
   在一個免費的拍照功能上單獨加一個閘，是把最嚴的門裝在最不重要的房間。
2. **生日是選填的，閘擋不到人。** 沒填生日的使用者要嘛全部放行（閘無效）、
   要嘛全部擋掉（擋掉多數真實使用者）。兩個結果都不對。
3. **這是寶可夢週邊，小孩一定會用 —— 所以重點應該放在「大人看得到」而不是
   「小孩進不來」。**

建議的同意書文字：

> 未滿 18 歲請由監護人陪同使用，並由監護人確認上面這些說明。

**但有一條我建議不要省**：如果 D-4 採納強制登入，那使用者已經在註冊時
同意過會員條款（其中已含未滿 18 歲須監護人同意）。**這一句就是二次提醒，
而不是唯一一次告知** —— 那個差別在事後很重要。

### 5.4 一條我認為現在的同意書已經做對、不要動的事

`sendsSelfieOffDevice` 這個設計（讀碼，`face-swap.ts:79-88`）**不要改成寫死的
文案**。它讓「同意書說了什麼」跟「程式實際上做了什麼」綁在同一個值上，
換 adapter 時文案不可能忘記跟著改。

這是這個 repo 少見的「把合規變成型別問題」的做法，我認為它是對的。
第二階段唯一要做的是：真 adapter 回 `true` 時，**重讀一次那段文案**，
確認它描述的第三方跟隱私權政策第五節新增的那一列是同一個。

Generative AI Prohibited Use Policy
（https://policies.google.com/terms/generative-ai/use-policy，查核日 2026-09-04）
禁止的相關項目逐字：

> "using personal data or biometrics without legally-required consent."
> "Impersonating an individual (living or dead) without explicit disclosure, in order to deceive."

**判讀**：政策禁的是（a）沒有合法同意就用生物特徵、（b）以欺騙為目的的冒充。
「本人上傳本人的臉、產出明顯風格化而非寫實」**不落在禁止清單裡**。

**但注意第一句話的重量**：它把「有沒有取得法定同意」變成**我們的**義務。
這正好是 §5.2（第三人肖像）與 §5.3（未成年人）要處理的東西 ——

**OpenAI 是四家裡最嚴的**（若日後考慮換供應商要重看）：條款要求
express consent + all necessary rights 才能重現他人肖像。
⚠️ 這一條**沒有取到逐字原文**（官方頁面 WebFetch 被 403 擋），

### 5.6 IP 風險 —— 規格 §4.2 有一句話我認為它的把握過頭了

**這一節是這一輪查證出來、規格與第一階段都沒有處理的東西。**

規格 §4.2 說這個做法的優點之一是：

> 使用者的卡是照片原樣貼上，絕不經過 AI 重繪，不會被改圖，**也避開重製他人
> 著作的問題**

**最後那半句我認為不成立，而且有一件已立案的聯邦訴訟指向反方向。**

**The Pokémon Company International, Inc. v. Frasier（Pokellector），2014-01-23
於美國聯邦法院立案。** 起訴狀 PDF：
https://cconnect.s3.amazonaws.com/wp-content/uploads/2014/01/DN1-Pokemon-Complaint.pdf
（查核日 2026-09-04）。Pokellector 是一個收藏管理 App，顯示卡牌圖片，
TPC 同時主張著作權（"unauthorized copies of Pokémon cards"）與商標。

**關鍵在於：那些卡圖是使用者提供的，不是營運者掃描的 —— TPC 還是告了。**
也就是說「這是使用者拍自己的卡」這條辯護，在這個案子裡已經被直接跨過。

⚠️ **結案結果查不到**（公開來源沒有報導）。**所以這不是一個判決先例**，
它證明的只有一件事：**TPC 願意為了卡面圖片提告。** 這比「有沒有贏」更貼近
我們要評估的風險。

另外兩件相關的：

- **拍照不會產生新的權利。** Bridgeman v. Corel（36 F. Supp. 2d 191, S.D.N.Y. 1999，
  https://law.justia.com/cases/federal/district-courts/FSupp2/36/191/2413183/）：
  忠實翻拍平面作品不產生新著作權（"the change of medium is immaterial"）。
  **推論**：所以成品裡那塊卡面區域，在法律上等同一份卡面美術的重製件。
- **First sale（17 U.S.C. §109）救不了。** 它涵蓋轉售／出借／展示**那個實體物**，
  不涵蓋重製權與改作權。（**推論**，法條適用，非引用判例。）

#### 但這個類別本身十幾年沒有執法紀錄

**查過之後的「沒有先例」，不是漏查**：針對 trainer card generator /
Pokémon card maker 這整個類別，**查不到任何一件有來源的 DMCA 下架、
C&D 或訴訟**。mypokecard.com、pokecardmaker.net、pokecard.net 都還在線上，
pokecardmaker.com 甚至販售實體印製的自訂卡。
Pokécharms 的 Trainer Card Maker 從 2005 做到現在（2024 年底關過一次，
**原因是營運成本不是法律**，2025-10 復活，
https://www.pokecharms.com/news/why-we-need-your-help）。

TPC 的執法其實很密集，但**全部是別的類型** —— Pokémon Essentials（fan game
製作工具）、Relic Castle（fan game 論壇）、Pokémon Uranium/Prism、
Pokeprincxss（網紅用 Poké 註冊商標）。**共通點是「重現遊戲本體」或
「用名稱做商業品牌」，我們兩者都不是。**

TPC 前法務長 Don McGowan 講過實務上的觸發條件
（Aftermath 訪談 2024-03-13，
https://aftermath.site/pokemon-lawyer-cease-desist-fan-project-pikachu-movie/）：

> "get[s] funded (for a Kickstarter or similar); if they get funded then that's when you engage."
> "the worst thing on earth is when your 'fan' project gets press, because now I know about you."

**門檻是「變現 + 曝光」，不是技術上是否侵權。**

#### 一件跟這個功能無關、但這一輪順帶查到的事

**"Poké" 字樣與寶貝球造型是 Nintendo 明確主張的商標標的，而且執法門檻極低。**
2026-02，紐約一家單店 TCG 店 The Poké Court 在遭持槍搶劫、登上國際新聞後幾週內
被 Nintendo 接觸，要求同時改掉**名稱裡的 "Poké"** 與 **logo 裡的寶貝球圖形**
（https://kotaku.com/pokemon-poke-court-nintendo-trainer-nyc-store-robbed-2000669827，
查核日 2026-09-04）。

**這跟訓練家卡沒有關係，但跟這個站有關係** ——
`AppBottomNav.vue` 的中央按鈕就是一顆寶貝球（讀碼，第 56–70 行的
`vdBallClip` / `vdBallShade`）。**這是既有的曝險，不是這個功能引入的**，
所以不該由這個功能的規劃來處理。**但它應該被記下來**，
建議另開一條進 [open-issues.md](open-issues.md)。

| | |
|---|---|
| 風險最高的一環 | **把實體卡照片合成進成品**（唯一有已立案訴訟支撐的環節） |
| 風險次高 | 產品名／網域／UI 出現 "Poké" 或寶貝球（**既有曝險，非本功能**） |
| 風險乘數 | 變現 + 媒體曝光（不是風險來源，是放大器） |
| 風險最低 | 原創訓練家卡 + 使用者自己的臉（十幾年零執法紀錄） |

**我不建議因此砍掉貼卡功能** —— 那是整個產品的核心，砍了就沒有產品了。
但我建議三件成本極低的事：

   不得出現在任何對外素材」）。**照做，而且要當成硬規則不是建議。**
2. **不要變現這個功能。** 這跟 §4.1「收點數是配給不是收入」的結論剛好一致 ——
   兩條不同的理由指向同一個做法。
3. **不要推廣。** 這跟 D-1（不當引流工具）也一致。McGowan 那句
   "the worst thing on earth is when your fan project gets press" 講的就是這件事。

**注意這三條全部跟 §4.1 與 D-1 的結論相同。**
成本論證與 IP 論證各自獨立地得到同一個答案，這讓 D-1 的建議更站得住。

**最後一條，關於 AI**：Nintendo 社長古川俊太郎 2026-07-03 股東 Q&A 官方逐字稿：

> "Regardless of whether generative AI is used, if Nintendo determines that
> something infringes on Nintendo IP, our policy is to respond appropriately."

（https://www.gonintendo.com/contents/62284-nintendo-comments-on-generative-ai-and-is-watching-for-any-uses-that-infringe-on）

**「這是 AI 生成的」既不加重也不減輕風險，它不是抗辯。**

## 六、入口與定位

### 6.1 這功能是什麼

**我的建議（D-1）：留存與好玩，不是引流。** 依據在 §4.1 ——
抽成 0%、金流未接通，引流帶進來的人期望收入是零。

- **不推廣、不買廣告、不放在首頁**

  理由回來」，不是「陌生人因為它而註冊」
- **成功的衡量標準不是新註冊數，是「做過卡的人的回訪率 vs 沒做過的人」**。
  這個數字站上量得到，而且它才是「留存工具」成不成立的答案

## 七、第一階段自陳的技術債，逐條判斷

第一階段的 commit 訊息與程式註解裡有幾條自陳限制。**逐條給優先度與我的判斷。**

### T-0（新增，不在原本的清單裡）成品頁主要按鈕被寶貝球蓋住

**優先度：最高。上線前必修。**

實測依據見 0.3。這一條不在第一階段的自陳清單裡，因為它是這一輪才發現的。

**為什麼排最高**：誤觸的後果是成品永久消失（規格 §5 C-3），
而且使用者不會知道發生了什麼。這是唯一一條「功能正常運作但使用者會失去成果」
的問題。

**建議修法**（兩個都做）：

1. `.page.tc` 的 `padding-bottom` 現在是 `calc(60 * var(--u))`
   （`TrainerCardPage.vue:596`，在 375px 上實測算出來是 **46.8px**，
   而導覽列高 57px、寶貝球還高出 21px）。
   **改成至少 `導覽列高 + 寶貝球突出量 + 安全間距`**，
   而且要用站上既有的那個值來源，不要再寫一個新的魔術數字。
2. **P6 落地時把成品捲到視野中央**（或把儲存按鈕做成不會落在寶貝球正上方的
   版面）。第 1 點解決「按鈕在頁尾被蓋住」，第 2 點解決「使用者落地那一幀」。

**驗收**：見 §8 S-0 —— 這條的驗收必須是**遮擋檢查**（`elementFromPoint`），
不能只是尺寸檢查，因為尺寸檢查現在就是過的。

### T-1 外框顏色寫死，沒有走 design tokens

**優先度：不做（但要改註解）。這是我認為最值得講的一條。**

現況（讀碼，`compose.ts:160-190`）：`#17161a`、`rgba(247, 59, 32, .85)`、
`rgba(13, 12, 15, .82)`、`rgba(244, 241, 238, .28)`、`#f4f1ee` 五個字面值。

而第 155–158 行的註解說明為什麼要用程式畫而不是一張 `frame.png`：

> 框的顏色要跟站上的權杖一致（深淺兩套主題都成立），而 PNG 沒辦法跟著變。

**我認為這個理由是錯的，而寫死的程式碼反而是對的。**

理由：這張圖是**匯出的成品**，使用者存進相簿、分享到社群。
它離開瀏覽器之後就沒有「主題」這回事了。
**如果外框跟著產生當下的主題變色，那同一個人在淺色模式與深色模式做出來的卡
會長得不一樣** —— 對一個要拿去分享、要有辨識度的東西來說，那是缺點不是優點。

規格 §4.2 自己說得很清楚：「構圖永遠一致 —— 每個人拿到同樣構圖」。
**顏色也該一致。**

**所以建議：程式碼不動，把註解改成講真正的理由**（匯出的成品需要跟觀看環境
無關的固定外觀；用程式畫是為了名字的字級自適應與省一張 PNG，不是為了跟主題）。

這條的價值不是省下工，是**避免有人照著那段註解去做一個會讓成品不一致的「修正」**。

### T-2 `frame.png` 不存在

**優先度：不做。** 見 0.4 —— 規格 §6.2 列的四個檔裡有 `frame.png`，
實際上外框是程式畫的，而且（照 T-1 的理由）應該繼續是程式畫的。

**要做的只有一件事：把規格與實作的差異記下來**，
否則下一個接手的人會照規格去找一個不存在的檔案。這份文件的 0.4 就是那個紀錄。

### T-3 自動偵測卡片邊緣還沒做，只有手動拖四角

**優先度：不做（至少第二階段不做）。**

`QuadEditor.vue:5-14` 的註解已經把理由講完了（讀碼），而且我認同：
自動偵測會失敗（花紋桌布、反光、旁邊有別張卡），失敗分支的答案還是
「請使用者自己標」，那不如先把那條路做對。

**我這一輪實測補一個依據**：我自己拖四個角的體驗是清楚的 ——
四個紅點很大、拖曳中會上移避免手指擋住、右邊即時顯示「校正後」的樣子。
**使用者看得懂自己在做什麼**，這比「自動猜對八成」有價值，
因為猜錯的那兩成使用者不知道該怎麼辦。

而且註解第 12–13 行說得對：之後要加自動偵測是**加成「先自動猜一次，
四個角照樣可以微調」**，這個元件不用改。**所以延後的成本是零** ——
這是延後決策的最好情況。

### T-4 P5 等待畫面下方是大片空白，站台頁尾就在那裡

**優先度：低，但建議跟 T-0 一起做（同一個版面問題）。**

實測（見 0.5）：P5 生成中的畫面，內容只佔上半部，下面是空白，
而站台頁尾（會員條款・隱私權政策）顯示在那個空白裡，**使用者在等待的 20 秒
內看得到也點得到**。點下去就離開頁面，這一次生成的錢就白花了。

跟 T-0 是同一類問題（頁面沒有把「這是一個不能中途離開的流程」表達在版面上）。

## 九、我認為不該做的

**這一節比「該做什麼」有價值，因為它省下的是還沒發生的工。**

| 不該做 | 理由 |
|---|---|
| **不要開 Cloudflare Pages / Pages Functions** | 規格 §6.3 的前提在這個專案不成立。開了就是為一個端點養第二套部署、第二份 secret、第二個 CI，還要為此開 CSP 的洞（§3.1） |
| **不要做自動偵測卡片邊緣** | 失敗分支的答案還是「請使用者自己標」，而那條路已經做好了。延後成本是零（T-3） |
| **不要把外框顏色改成走 design tokens** | 匯出的成品不該跟著觀看者的主題變色，那會讓同一個人在不同主題下做出不一樣的卡。該改的是那段註解（T-1） |
| **不要在第一版做多張樣板** | 成品的差異度已經由使用者自己的卡提供（佔畫面 32%×30%）。加樣板是最貴的做法，而且加在不重要的那一半（§2.2） |
| **不要做鑑定卡（PSA/BGS）** | 規格 §4.4 已經用實測否掉：比例差 20%，對齊高度兩側各露空 49px，對齊寬度上下溢出 166px。要做就得另生一張樣板，那是另一個專案 |
| **不要不登入就開放** | 沒有收入對應的支出必須有可歸屬的上限，而 CGNAT 讓 IP 限流同時誤傷真人又擋不住有心人（§4.3） |
| **不要把成本回收記成收入** | 金流未接通、抽成 0%，收點數是配給不是收入。記錯會讓之後所有成本決策建立在假數字上（§4.1） |
| **不要做人臉比對／活體偵測來擋第三人肖像** | 站上沒有基準人臉可比對，做一個管不到的機制會讓責任從「有告知」變成「宣稱會擋但沒擋住」（§5.2） |
| **不要做硬性年齡閘** | 生日是選填的，閘要嘛無效要嘛擋掉多數真人；而且抽卡本身都沒有閘（§5.3） |
| **不要把 429 加進自動重試** | 已經寫死在 `AUTO_RETRYABLE` 外面，`face-swap.ts:48-52` 也寫了警告。規格 §8.1 說這是前專案踩過的雪崩。**維持現狀，不要「優化」它** |
| **不要存自拍去做「歷史紀錄」功能** | 規格 §5 C-2 是硬約束，而且它正是同意書敢那樣寫的唯一理由。一旦存了，整個隱私論述要重寫 |
| **不要做分享連結或 QR** | 規格 §5 C-1 明訂。成品用系統分享直接進相簿，不做跨裝置傳遞 |
| **不要在任何對外素材放真實寶可夢卡的圖** | 規格附註已寫，但要當硬規則。示範圖一律用自製的佔位卡（`make_warp_fixture.py` 產生的棋盤格就可以）（§5.6） |
| **不要為了省 NT$1.9/張換掉 Gemini** | FLUX.1 Kontext pro 確實便宜六成，但換供應商等於把 §10.3 那五個 prompt 地雷重踩一遍。留著當日後量大時的退路就好（§4.2） |
| **不要因為 IP 風險就砍掉貼卡功能** | 那是整個產品的核心，砍了就沒有產品。該做的是不變現、不推廣（§5.6） |
