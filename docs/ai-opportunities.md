## 先講三句結論

**一、這個產品現在最痛的地方，一項都不是 AI 能解的。**

| 現在最痛的 | 出處 | AI 有沒有幫助 |
|---|---|---|
| 正式站陳列的 32 個池 **100% 是假池**，一個真實賣家開的都沒有 | `open-issues.md` P-1／P-5（實測） | 沒有 |
| F-1〜F-6：買二手卡按回收，**點數付給前一個主人** | `open-issues.md` 第一節（實測） | 沒有 |
| 手機動線 11 條，其中 6 條是「功能對、但使用者做不到」 | `mobile-ux-audit.md`、commit 13b8b62 | 沒有 |
| V-1 鎖序相反造成的死鎖環 | `open-issues.md` 第九節 | 沒有 |
| L-1／L-2 只做完卡冊那一半，市場那一半還沒補 | `open-issues.md` 第五節 | 沒有 |

**任何 AI 工作都不該排在這五件事前面。** 如果現在只有一個人在做事，這份文件應該先擱著。

**二、真正有位置的 AI 只有一個形狀**：把**照片或自由文字**翻譯成**結構化欄位**，而且輸出只能是**建議或風險分數**，不能是決定。凡是輸出會直接動到錢、卡的歸屬、或公平性承諾的，全部不行。

**三、使用者問過的「拍照掃描辨識卡片文字」——值得做，但第一步不是 AI。**
這條線真正的價值不在「省下打字」，在**讓賣家不用會打日文**。目前建一個 30 張卡的池要 200+ 次互動，其中最卡的一步是「在 TCGdex 目錄裡用日文卡名搜尋、再從一片相似縮圖裡認出正確那張」（`src/components/CardPicker.vue`，日文卡名是唯一準確的搜法）。鑑定標籤上印的是**英文／羅馬字**的套牌與卡號，如果那組資訊對得回 TCGdex 的 `setCode-cardNo`，就直接餵得進既有的目錄查詢（`src/lib/tcgdex-catalog.ts` 的 `?id=eq:SV4a-349`，實測支援 `eq:`）。所以拍照的價值是**繞過日文輸入**，不是省下抄 8 位數。詳見提案一。

> ⚠️ **這一段有一個我沒有查證的前提，而整個提案一的價值都靠它：**
> PSA 標籤上寫的是套牌的**英文名稱**（例如 `SHINY TREASURE EX`）還是 TCGdex 用的**代碼**（`SV4a`），我沒有實際看過日版鑑定卡的標籤原件。
> 如果是英文名稱，就多一層「英文套牌名 → TCGdex setCode」的對應（那是一張固定的查表，做得出來，但要有人建），
> 而 `research-card-pricing.md` 2.3 節警告過「日英套牌對應在數學上不存在」——**那句話講的是卡片層級**，套牌層級的對應應該是做得到的，但沒查證。
> **動工前的第一件事應該是拿三張真實的日版 PSA 卡拍照，看標籤到底印什麼。** 這件事花不到一小時，而它決定這個提案成不成立。

## 一、提案：拍鑑定標籤 → 預填欄位 + 一致性檢查

**這是我排第一的，也是「只能先做一件事」的答案。第六節有可以直接開工的草圖。**

### 它解決誰的什麼問題

**賣家建池與登記卡片時的重複勞動，以及「平台不知道賣家手上有沒有那張卡」。**

- 建一個 30 張卡的池 ≈ **200+ 次互動**（`SellerNewPoolPage.vue`：挑卡器最多 60 張，每張要「搜尋 → 認縮圖 → 選變體 → 賞別 select → 數量 → 買回價覆寫」）。
- 「以既有的池為範本」對鑑定卡**刻意失效**——`certNo`/`grader`/`grade` 被抽掉並標 `needsRepick`。所以 60 張鑑定卡的池，範本一點忙都幫不上。
- 登記一張卡（`CardUploadPage.vue`）只能一次一張，註解明講「要登記三張就走三次」。要登記 20 張就是 20 趟完整流程。
- 搜尋最準的寫法是**日文卡名**。台灣卡舖老闆不一定打得出「リザードン ex」。
- 而 `open-issues.md` P-5 的實測結論是：**正式站 32/32 是假池，一個真實賣家的池都沒有。** 上架摩擦是這件事的其中一個原因。

另一半：`HANDOFF.md` 4.2 最後一句記著使用者親口問過而至今沒有答案的問題——
「**萬一上傳的卡片是沒有經過檢驗的卡片，我該怎麼知道他是否真的持有這張**」。
`open-issues.md` U-6 也記著同一件事：`prizes.status = 'stashed'` 是被**宣告**的，從來沒被驗證過。
一張**現拍的**標籤照片，本身就是這個問題的一半答案。

### 不用 AI 的話怎麼解，為什麼那樣不夠

這一項要拆成三段看，**只有第三段該用 AI**：

| 要拿到的東西 | 不用 AI 的解法 | 夠不夠 |
|---|---|---|
| **鑑定編號 certNo** | **掃條碼／QR。** PSA 新標籤背面的 QR 編碼的就是 cert 驗證頁連結（`cert-verification-alternatives.md` E-4 已查證），舊標籤正面有一維條碼 | **夠，而且比 AI 好。** 條碼有校驗、確定性、零邊際成本。這一欄是 `prizes_cert_alive` 唯一索引的鍵，讀錯一位就是把別人的卡登記到自己名下——這種欄位不該交給會猜的東西 |
| **卡片身分（卡名／卡號／變體）** | **既有的 TCGdex 目錄挑卡**（`src/lib/tcgdex-catalog.ts` + `CardPicker.vue`）。`docs/rules.md` 明講「卡是**挑**出來的，不是打字打出來的」 | **夠，而且目錄才是權威。** 問題只在「怎麼把搜尋字串填進去」 |
| **標籤上其餘的印刷文字**（set code、卡號、分數、鑑定公司、英文卡名） | 傳統 OCR（tesseract.js）；或什麼都不做，讓使用者自己抄 | **不夠。** 見下 |

第三段為什麼不夠：

- **傳統 OCR**：壓克力殼反光是常態、手持一定歪斜、標籤版面 PSA／BGS／ARS 各不相同。tesseract.js 要帶 2–4MB wasm + 訓練資料進 bundle，而這個 repo 的前端**只有三個 runtime 依賴**（`vue`/`vue-router`/`pinia`）——加這麼大一包要有很強的理由。而且它只吐文字，不會告訴你「這串字是 set code 還是 grade」，版面解析還得自己寫，PSA 一改標籤就全壞。
- **什麼都不做**：那就是現況，而現況是 0 個真實賣家的池。

VLM 在這裡真正的優勢有兩個，都不是「認字」：
1. **它同時回答「這串字是什麼欄位」**——輸出直接是 `{setCode, cardNo, grade, grader}`，不需要版面模板。
2. **它能做跨模態比對**：照片上的卡圖／標籤文字 vs 賣家在表單裡填的目錄卡。這正是 `cert-verification-alternatives.md` 方案 D 判定為「本次調查中最被低估的一條」的那件事，而且**完全不碰 PSA 的條款**（處理的是使用者上傳到自家平台的圖）。

> 附帶說明：那份研究推薦的是 Ximilar `/v2/slab_id`（專門的 slab 標籤 OCR）。它的問題是**單價查不到**（定價頁只給 credit 計算機），而且它只回文字欄位、不做第 2 點的跨模態比對。用通用 VLM 的理由是「一次呼叫同時得到兩個用途，而且價錢是公開的」。要不要改用 Ximilar 是可以之後量測後再換的事——端點形狀一樣。

### 失敗會怎樣

這是這份提案裡最需要講清楚的一節，因為這是一個牽涉真錢與實體卡的平台。

| 失敗樣態 | 代價 | 防線 |
|---|---|---|
| **certNo 讀錯一位** | **最嚴重。** `prizes_cert_alive` 是 `unique(grader, cert_no)`。填錯 → ①把別人的合法卡擋掉（他被迫去開接管工單）②或自己的卡被登記成不存在的編號，之後買家查 PSA 查不到 | ①certNo **優先取條碼**，不取 OCR ②條碼與標籤文字不一致時 **兩個都不預填**，把兩個值並列讓賣家選 ③預填的值一律可改，送出前顯示「這是自動讀的，請核對」 |
| **set code／卡號讀錯** | 目錄查詢查不到或查到別張。賣家看得到縮圖，會發現 | 讀出來只是**搜尋條件**，最後仍然是賣家從候選裡點選。錯了就是多打一次字，等同現況 |
| **一致性檢查誤報**（照片跟填寫其實是對的，卻判成不符） | 賣家被丟進人工佇列，摩擦。在只有個位數賣家的階段，這比放過一張可疑卡糟糕得多 | **不硬擋。** 只記風險分數。`cert-verification-alternatives.md` E-1 已經定過這條原則：「保守，寧可放過不要誤殺」 |
| **一致性檢查漏報**（照片跟填寫真的不符，卻沒抓到） | 一張描述不實的卡進了池 | 今天的基線是 **0% 召回**——完全沒有這個檢查。任何 >0 的召回都是淨賺。而且後面還有出貨違約累積那道防線（`rules.md` 第五節） |
| **模型讀不出來** | 沒有預填，退回手動 | 提示詞明講「看不清楚就回 null，不准猜」，回傳 `unread` 陣列 |
| **服務逾時／429／5xx** | 使用者卡在轉圈 | 整塊「拍照預填」收起來，退回既有手動流程，**一個字都不提辨識這件事**。這是加值路徑，它壞掉不該讓使用者知道自己踩到了什麼 |

**一條絕對不能破的線：這條路徑不可以擋住登記。**
`cardbook.ts:94-130` 已經示範過正確的形狀——PSA 查不到時標 `pending`、不硬擋，要不要強制由 `PSA_VERIFY_ENFORCE` 環境變數決定。掃描應該完全比照，而且連那個開關都不要有。

### 大概多少成本

以 `claude-opus-5` 為預設（$5 / $25 每 MTok）。要不要為了成本降級是商業決定，所以三級都算給你。
影像 token 的依據：Opus 5／Sonnet 5 屬高解析度層，長邊上限 2576px，**單張最多約 4,784 個影像 token**；Haiku 4.5 仍是舊層（1568px、約 1,600 token 上限）。
`src/lib/image-edit.ts` 的 `ticket-doc` 政策輸出長邊 **2400px**，正好落在高解析層的上緣，所以估 **4,000 影像 token**。
每次呼叫另計系統提示與卡片欄位約 700 token、結構化輸出約 200 token、adaptive thinking 約 400 token。
匯率以 **US$1 ≈ NT$32** 換算（假設值，實際請以當時匯率為準）。

| 模型 | 單次 | 1,000 張／月 | 10,000 張／月 |
|---|---:|---:|---:|
| `claude-opus-5` | $0.0385（NT$1.23） | $38.5（NT$1,230） | $385（NT$12,300） |
| `claude-sonnet-5` | $0.0154（NT$0.49） | $15.4（NT$493） | $154（NT$4,930） |
| `claude-haiku-4-5` | $0.0053（NT$0.17） | $5.3（NT$170） | $53（NT$1,700） |

**換個角度看這個數字**：一個 60 張卡的池，用 Opus 5 掃完是 **$2.31 ≈ NT$74**。
那個池若是票價 300 點、賣 200 張，票收是 NT$60,000。**辨識成本是票收的 0.12%。**
這個量級下，為了省錢降級是不划算的交換。

**但我不建議用 Haiku 4.5，而且理由不是「它比較笨」**：它的影像上限是 1568px。
而 commit `970e0a4` 花了一整輪實測才定出「1200px 是 8 位數編號的可讀下限、2400px 是留一整級餘裕的選擇」。
用 Haiku 4.5 等於把那一級餘裕丟掉，退回距離下限只有 1.3 倍的地方——
而那個餘裕正是這個團隊自己量出來、自己決定要付的。

三件關於成本的技術細節，避免估算失真：

- **不要用 Batch API。** 它便宜一半，但賣家在螢幕前等。留給「夜間對已上傳照片重掃一輪」那種用途。
- **prompt caching 在這裡幫助有限。** 固定前綴只有 ~700 token，而最小可快取前綴依模型是 512–4096 token，很可能根本快取不到；而且 85% 的 input token 是每次都不一樣的圖片。**不要把 caching 的折扣算進預算。**
- **`stop_reason: "refusal"` 要處理。** 賣家的桌面可能不小心入鏡身分證之類的東西，安全分類器有機會擋下。要在讀 `content` 之前先檢查 `stop_reason`，並且照官方建議帶上 server-side `fallbacks`（`betas: ["server-side-fallback-2026-07-01"]` + `fallbacks: "default"`）。

### 送了什麼給外部服務、風險是什麼

**送出**：一張鑑定卡的照片、賣家填在表單裡的卡片欄位（卡名／卡號／鑑定公司／分數／編號）。
**不送**：使用者 id、姓名、地址、電話、email、會員編號、餘額、任何訂單資訊。

三個要在隱私權政策裡寫明的風險：

1. **照片背景**可能拍到桌上的個資（包裹面單、證件）。對策：這個用途的 `EDIT_POLICY` **不可以是 null**，裁切是必經的一步，而且要在裁切畫面上寫出「這張圖會送到影像辨識服務」。
2. **鑑定編號是「可以拿去別處登記的東西」**——這正是 L-2 把 `certNo` 從公開 API 拿掉的理由（`server/src/card-public.ts` 的白名單）。送給模型供應商跟送給全世界不是一回事，但仍然是一次對外揭露，要在「影像處理委外對象」那一節列名。
3. **資料保留**：Anthropic API 預設有保留期。若要零保留，那是企業層級的設定，要先確認再上線。

## 二、提案：卡舖的庫存清單（自由文字）→ 目錄對應

### 它解決誰的什麼問題

同一個痛點的另一半：`docs/deck/` 有一份「給卡舖卡商的合作簡報」（commit 9ae2dc8）。
**卡舖的庫存本來就在他的 Excel／POS 裡**，格式通常是一行自由文字：

```
リザードンex SAR sv3 125/108 PSA10 82345671
牡丹SAR  SV4a-354  BGS9.5  0016123456
```

要他把 100 行逐一在挑卡器裡重打一次，這件事本身就是不接受合作的理由。
`SellerNewPoolPage.vue` 全檔 **grep 不到任何 CSV／匯入／批次建立**。

### 不用 AI 的話怎麼解，為什麼那樣不夠

**先做 CSV 範本，而且我認為那就夠了，先不要用 AI。**

給一份欄位固定的 CSV 範本（`setCode, cardNo, grader, grade, certNo, tier, qty, buyback`）+ 一個欄位對應 UI，
再加上「貼上後逐列顯示目錄查到的縮圖，全部確認才送出」。
這是確定性的、可以寫迴歸測試的、不用錢的，而且**卡舖只要學一次**。

AI 的位置只在一種情況才成立：**卡舖抱怨他的匯出格式對不上範本，而且他改不了**（POS 系統是別人的）。
那時「自由文字 → 欄位」是個真的翻譯問題，規則式寫不完（每家 POS 的欄位順序、分隔符、卡名寫法都不同）。

**所以這一項的判斷是：先做 CSV，不要用 AI。等到真的有卡舖因為格式問題卡住，再用 AI 補那一段。**

### 失敗會怎樣

輕。轉換結果**逐列**顯示目錄查到的卡圖與變體，賣家一列一列確認才送出。
猜錯的代價是他要手動改那一列——比現在從零打字仍然好。
唯一要守的是：**變體（`variantId`）永遠不准由轉換結果決定**（見第三節第 7 項）。

### 大概多少成本

純文字，很便宜。100 行清單約 2,500 input token、4,000 output token（100 列結構化輸出）：

- `claude-opus-5`：$0.113 / 100 張 ≈ **NT$3.6**
- `claude-sonnet-5`：$0.045 / 100 張 ≈ NT$1.4

一個月轉 50 份清單也不到 $6。這一項的成本基本上不用討論。

送出的是**卡片清單文字**，不含任何使用者身分資訊。風險比提案一低（沒有圖片，就沒有背景入鏡的問題）。

### 要多少工

CSV 範本 + 對應 UI：**3 天**。
AI 自由文字轉換（真的需要時再做）：再 **5 天**。

## 三、提案：接管工單的「時間戳照片」預審

### 它解決誰的什麼問題

**客服的人工判讀。** `inventory-first-plan.md` 第六節定義了站外轉手的接管流程：
新持有人要提交**時間戳照片**——卡背鑑定標籤 + 手寫紙條**同框**，紙條寫今天日期 + 平台名 + 他的會員編號。

客服要判斷四件事：①標籤與紙條在同一張照片裡 ②標籤上的編號就是申請的那個 ③紙條上的日期是近日 ④紙條上的會員編號是申請人本人。
這四件事機械、重複，而且都在圖片裡。

`tickets.ts` 的 `applyTakeover()` 結案時會**同時改 `user_id` 與 `custodian_id`**——這是全站唯一「擁有權與實體同時易主」的路徑。所以判錯的代價很實。

### 不用 AI 的話怎麼解，為什麼那樣不夠

- ①③④ 涉及**手寫字**。傳統 OCR 對手寫幾乎沒用。
- ② 標籤上的印刷編號可以靠條碼——但接管照片是「卡背」，而條碼在正面標籤，這一段條碼幫不上。
- 完全不做就是現況：客服每一張都要人眼看。

所以這一項**確實需要視覺理解**，沒有規則式替代品。

**但它排第三，理由是量。** 現在的工單量幾乎是 0（產品還沒有真實賣家）。
在一天不到十張單的時候，做這個是在替一個還不存在的瓶頸最佳化。
**等到接管單一週超過 20 張再做。**

### 失敗會怎樣

**輸出只能是「給客服看的預審摘要」，不可以自動結案。**
`tickets-contract.md` 第一節的設計原則寫得很死：「工單是前門，不是新的金流」，
驗收標準是「把 tickets 兩張表 drop 掉，錢跟權限都還是對的」。
一個會自動結案的 AI 直接違反這條——`applyTakeover()` 會動卡的歸屬。

正確的形狀：模型回四個布林值 + 讀到的編號與日期，客服看著這四格做決定，**按下結案的仍然是人**。
誤判的代價因此只有「客服多看一眼」。

### 大概多少成本

兩張圖（標籤特寫 + 紙條同框），約 8,000 影像 token + 700 提示 + 1,000 輸出：

- `claude-opus-5`：**$0.0685 / 單 ≈ NT$2.2**
- 一個月 20 張單 → **$1.4**。可以忽略。

**送出**：兩張照片，其中一張含**手寫的會員編號與日期**。
會員編號（`users.member_no`）是平台內的身分識別碼——這是這三項提案裡唯一會把使用者識別碼送出去的一項，要在隱私政策裡單獨講。
**不送**：姓名、地址、電話。

### 要多少工

**3–5 天**，前提是提案一的呼叫骨架已經在了（同一套結構化輸出、同一套錯誤分流）。單獨做的話 1.5 週。

## 四、提案：跨語言卡片同一性（PSA 英文 ↔ TCGdex 日文）

**這一項本身是對的，但它現在跑不到，所以排最後。**

### 它解決誰的什麼問題

`server/src/card-cert.ts` 的 `cardNumbersAgree()` 有一段誠實的自白：
因為 **PSA 回的是英文、目錄是日文，卡名不可能字串相等**，所以它只比卡號的數字部分，
**比不出來就回 true（不擋）**，交給賣家自己勾 `certConfirmed`。

那個「賣家自己確認」在實務上就是橡皮圖章——他當然會勾。
`research-card-pricing.md` 2.3 節的標題直接寫著「日英套牌對應在**數學上**不存在」，
所以這件事沒有規則式解法：`CHARIZARD EX` 對上 `リザードン ex` 是同一張嗎，只能靠語言知識判斷。

這是純文字、極便宜（`claude-opus-5` 約 **$0.011 / 次 ≈ NT$0.35**），而且只在 mismatch 分支才觸發。

### 為什麼排最後

**因為那條分支今天永遠走不到。**

`server/src/psa.ts` 的 PSA API 目前全部回 403（`open-issues.md` X-1，帳號待核准）。
`verifyCert()` 因此回 `api_unavailable` → `psaStatus = 'pending'` → **`CERT_MISMATCH` 那個 409 分支一次都不會執行**。

所以這一項是**卡在 X-1 的下游**。現在做了，等於寫一段跑不到的程式碼。
X-1 解了再做，而且到那時要先確認 X-2（PSA EULA 能不能把資料顯示給買家）。

### 失敗會怎樣

**輸出只能是「給賣家看的第二意見」，不可以自動放行。**
今天的預設是「賣家自己勾確認」；如果 AI 說「是同一張」就自動通過，
等於把一個有名有姓的人的確認，換成一個沒有人負責的判斷——**那是責任的降級，不是升級**。
正確的形狀是：把模型的判斷跟理由**顯示在那個核取方塊旁邊**，勾的還是賣家。

### 要多少工

**2–3 天**。但先解 X-1。

## 五、明確不該用 AI 的地方

### 1. 抽選結果、機率、籤序 —— 這是紅線，不是取捨

公平性靠 commit-reveal + drand 第三方隨機源，籤序在開賣前就以雜湊封存
（`src/shared/fairness.ts`，`COMMIT_VERSION = 4`）。
整份機制的價值就在於**沒有任何人（包括伺服器）可以介入**：
`Stream` 用 HMAC 產生決定性位元組流，`below(n)` 用拒絕取樣而不是取餘數——
註解寫得很清楚，取餘數的偏差雖然極小，但「很小」在公平性驗證裡等於「有」。

一個連取餘數的偏差都不肯接受的系統，不可能容納一個機率性的模型。
**這件事連討論都不該開始。**

### 2. 買回價與參考價的定價建議

三個各自獨立、都足以否決的理由：

1. **法律**：買回價是**賣家宣告並承諾**的債（`rules.md` 第二節），寫進 manifest v3、開賣後改不了。平台給一個「建議金額」等於平台在替賣家的法律義務定價，而電子遊戲場業管理條例 §14-II-2 正是在禁止平台介入獎品的回購。
2. **架構**：`refPrice` 已經被**刻意降級**成「賣家標示的參考價、純顯示、不參與任何金額計算」（`HANDOFF.md` 4.1）。給一個不參與計算的欄位配一個 AI 估價，是在替一個已經拆掉的地基重新灌漿。
3. **技術**：真的要錨點的話，**確定性資料比模型準**。`research-card-pricing.md` 已經查完了——TCGdex 內建 Cardmarket `avg7`、免 key、免費、31/31 命中、當天更新。一個抓得到的真實成交均價，永遠贏過一個生成出來的數字。而且那份研究第五節那張對照表（refPrice 對 Cardmarket 從 0.10× 到 96.3×）證明了「一旦有錨點，離譜的數字會自己跳出來」——**不需要模型**。

### 3. 通知與錯誤訊息的措辭

`notifications-audit.md` 走了 45 個事件，把每一則的文案、`refId` 語意、`link` 是否可點都定死，
還為此寫了 25 條迴歸測試。`notify.ts` 的兩條硬規則之一是「同一件事只通知一次」，靠唯一索引 `notifications_once` 擋。

動態生成文案會破壞三件事：①同一件事每次講法不一樣（在一個算錢的系統裡這是災難）②迴歸測試沒有東西可以斷言 ③**模型會加 emoji**，而手機 UI 不能有 emoji。

錯誤訊息更是如此：`open-issues.md` L-4 剛剛才把三個 `e.message` 外送改掉，換成固定中文訊息。
讓模型來寫錯誤訊息，等於把那個修正倒退回去。

### 4. 工單的自動裁決與自動回覆

`tickets-contract.md` 第一節：「工單是前門，不是新的金流」，驗收標準是
「把 tickets 兩張表 drop 掉，錢跟權限都還是對的」。
`resolve` 依 kind 會觸發 `applyTakeover()`（改卡的歸屬）、`act()` + `escrow.ts`（動託管的錢）、
或改 `seller_verifications`（改開池權限）。這三條全部要有一個具名的人負責，
而且 `admin_actions` 稽核就是為了記下「是誰決定的」。

自動回覆同理：`ticket_messages.is_staff` 特地存下來而不是 join role，
註解寫的理由是「權限可能事後收回，但『當時是客服說的』是歷史事實」。
一則沒有人說過的「客服說的話」，破壞的是這個欄位的語意。

### 5. 鑑定編號的格式與上限檢查

`cert-verification-alternatives.md` E-1 已經把這件事做完了：純數字、長度 7–9、值 ≤ 2 億（可調環境變數）。
那是**一個純函式**，一小時寫完、不需要網路、不需要任何人核准、零成本零風險。
`server/src/psa.ts` 甚至已經有 `invalid_format` 這條分支在等它。

用模型做這件事會更慢、更貴、而且**更不確定**。這是「規則式就夠了」的教科書案例。

### 6. 手機版面、觸控目標、無障礙

`mobile-ux-audit.md` 的 11 條，加上 commit 769c4a2（觸控目標補到 44px）、a3bf83c（17 處字重改成實際渲染值）。
這些是量出來的：`elementFromPoint` 打到什麼、按鈕在視窗下方幾 px、捲軸窗口 150px 塞 349px 的內容。
**量測比判斷可靠**，而且 `HANDOFF.md` 2.4 已經寫下了正確的量測方法。
這條路要投資的是更好的自動化量測，不是模型。

### 7. 卡片變體（`variantId`）的判定 —— 這一條最容易被漏掉

`variantId` 在 **manifest v4 裡**（`src/shared/fairness.ts`），也就是說它是**公平性承諾的一部分**，開賣後改不了。
而它的重要性有實測數字：同一組卡號 `SV2a-025`，普卡 Cardmarket €0.02、大師球鏡面 €369——**差約 18,000 倍**。

關鍵事實：**鑑定標籤上不會印變體。** 標籤只寫套牌與卡號。
所以任何「AI 判定變體」都是在猜，而猜出來的東西會被封進一個開賣後改不了的承諾裡。
猜錯的後果不是「填錯一格」，是**那個池對外看起來像被竄改**。

**變體必須由人從卡圖上選。** 這是提案一裡我唯一不肯讓步的欄位。

## 六、如果只能先做一件事

**做提案一：鑑定標籤拍照 → 預填 + 一致性檢查。**

選它的理由有三個，按重要性排：

1. 它同時打中**兩個**已經寫在文件裡的痛點：上架摩擦（P-1/P-5，32/32 假池）與「平台不知道賣家手上有沒有那張卡」（U-6 / `HANDOFF.md` 4.2 使用者親口問過的那句）。
2. 它是使用者本人問過的那條線的正確收斂——而且收斂的方向跟他當初直覺不同：**價值在繞過日文輸入，不在省下抄 8 位數**。
3. 它不需要動任何金流、公平性、或鎖序的程式碼。它是加在旁邊的一條路，壞掉就退回現況。

### 打哪個端點

**新增 `POST /v1/cardbook/scan`（`requireAuth`）。**

為什麼是新端點而不是塞進 `/v1/cardbook/upload`：

- `/upload` 是一筆會寫資料庫的交易。`cardbook.ts:95` 那則註解已經替這件事做過判斷了——
  「查證是網路 I/O，擺進交易會讓 DB 連線被 PSA 的往返時間佔著」。模型呼叫的往返比 PSA 更長。
- 掃描的結果**不能擋** upload。分開才不會讓辨識服務掛掉時整條登記路走不通。
- 建池頁（`SellerNewPoolPage.vue`）與登記頁（`CardUploadPage.vue`）都要用，掛在共用的地方。

### 資料怎麼進出

**進**：

```jsonc
POST /v1/cardbook/scan
{
  "fileId": "f-0123456789ab",     // 走既有的 presign 直傳，purpose: 'card-scan'（新增）
  "barcodeCertNo": "82345671"     // 選填：前端掃條碼／QR 讀到的。用來交叉比對，不是備援
}
```

用 `fileId` 而不是把 base64 塞進 body 的理由：`files.ts` 的設計是**位元組不經過伺服器**（presign 直傳 R2）。
後端拿 `fileId` 換一個 1 小時的 R2 簽名 GET 網址，用 `{"type":"image","source":{"type":"url","url":...}}` 的形式送給模型，
位元組仍然不經過我們的伺服器。代價要講明：那個簽名網址在有效期內對模型供應商的抓取器是可讀的。
（另一個選擇是後端自己抓下來轉 base64，揭露面一樣，但多一份記憶體與延遲。）

**出**：

```jsonc
{
  "read": {
    "grader":   "PSA" | null,
    "grade":    10 | null,
    "certNo":   "82345671" | null,
    "setCode":  "SV4a" | null,
    "cardNo":   "349" | null,
    "labelName":"CHARIZARD EX" | null,     // 標籤上的英文卡名，只給人看，不進任何比對
    "language": "JP" | "EN" | null
  },
  "unread": ["language"],                   // 讀不出來的欄位。明確列出，不猜
  "certNoSource": "barcode" | "label" | "both-agree" | "both-differ",
  "candidates": [ /* 用 setCode-cardNo 打 TCGdex 查回來的卡與其 variants */ ],
  "notice": "照片上讀到 PSA 10，編號 82345671（條碼與標籤一致）。"
}
```

三條設計紀律：

1. **模型只回結構化欄位，不回給使用者看的句子。** `notice` 由後端用固定模板拼。
   理由見第五節第 3 項——文案要可迴歸測試、不能有 emoji。
   實作上用 `output_config: {format: {...}}` 綁 JSON schema，避免解析失敗。
2. **`certNo` 的優先序是 barcode > label。** 兩者都有且不一致時 → `certNoSource: "both-differ"`，
   **兩個都不預填**，前端把兩個值並列讓賣家選。這是整份設計裡唯一「寧可不填」的欄位，因為它是唯一索引的鍵。
3. **`variantId` 永遠不出現在這個回應裡。** 見第五節第 7 項。

模型參數建議：`model: "claude-opus-5"`、`thinking: {type:"adaptive"}`、`output_config: {effort: "low"}`
（這是抽取任務不是推理任務）、`max_tokens: 2000`、以及 `betas: ["server-side-fallback-2026-07-01"]` + `fallbacks: "default"`。
讀 `content` 之前先檢查 `stop_reason`。

### 錯的時候使用者看到什麼

| 情況 | 畫面 |
|---|---|
| 服務 5xx／逾時／429 | 「拍照預填」整塊收起來，退回既有手動流程。**不提辨識、不提 AI、不顯示錯誤。** 後端 `console.error` + `monitor.ts` 加一條不變式 |
| 完全讀不出來 | 「這張照片看不清楚，可以換個角度再拍一次，或直接手動填」。不要說「辨識失敗」——那是我們的內部狀態 |
| 部分讀出來 | 讀到的欄位預填並標「自動讀取，請核對」，`unread` 的欄位留空。**部分預填也是預填** |
| 條碼與標籤的編號不一致 | 「照片上的編號有兩個讀法：條碼 82345671、標籤 82345677。請確認是哪一個。」兩顆按鈕讓他選，或自己打 |
| 一致性檢查判定不符 | **不擋。** 送出鈕旁邊一行提醒：「照片上讀到的是 PSA 9，你填的是 PSA 10，確定嗎？」加一個「我確認沒錯」核取方塊——**沿用 `cardbook.ts:105` 既有的 `certConfirmed` 形狀**，不要發明第二套 |
| 賣家勾了「我確認沒錯」 | 照常登記，但把 risk 記進 `prizes.card` 的一個欄位。**這個欄位不進 manifest**——理由同 `psaStatus`：它是會變的附註，綁進承諾會讓一次誠實的重新辨識看起來像竄改 |

### 怎麼驗證它有沒有變好

**先量基線，再接 AI。** 這一步不能省——沒有基線就沒有「變好」。

**離線評測**

- 標註集：至少 **150 張真實鑑定卡照片**（PSA／BGS／ARS 混、含反光／傾斜／暗光／舊標籤），人工標六個欄位。
- 另外造 **30 組「照片與填寫不符」**（拿 A 卡的照片配 B 卡的欄位），測一致性檢查。
- 三個指標，重要性由高到低：

  | 指標 | 目標 | 為什麼是這個數字 |
  |---|---|---|
  | `certNo` **錯讀率**（讀出一個值但值是錯的） | **< 0.5%** | 這是唯一索引的鍵。錯讀比未讀糟糕得多——未讀只是沒幫上忙，錯讀會擋掉別人的卡 |
  | 各欄位**精確率** | certNo ≥ 99%、其餘 ≥ 90% | 其餘欄位最後都會經過賣家從候選裡點選，錯了只是多打一次字 |
  | 一致性檢查的**誤報率** | < 5% | 100 張真卡最多 5 張被丟進人工佇列。在只有個位數賣家的階段，誤殺一個真賣家比放過一張可疑卡糟得多 |

- 一致性檢查的**召回率**沒有目標值，因為**今天的基線是 0**——完全沒有這個檢查。任何 >0 都是淨賺，前提是誤報率壓得住。
- 腳本放 `server/src/eval-cardscan.ts`，比照既有 `regress-*.ts` 的形狀，輸出逐欄位混淆矩陣。
  **不要掛進 CI**：每次跑都花錢，而且模型會變——那會讓一次無關的部署因為模型行為漂移而失敗。

**線上真值（我最推薦的一條，而且零成本）**

在 `monitor.ts` 加一條不變式：**「掃描後預填的 `certNo`，被賣家在送出前改掉的比例」**。

這一條之所以好：它不需要標註集、不需要人力、而且是持續的。
賣家改掉預填值 = 我們讀錯了（或至少他不信任那個值）。
比例上升就是模型漂移或標籤版本變了，`monitor.ts` 現有的十條不變式已經有「破了就開一張修復工單給管理員」的機制（commit 145e547），直接沿用。

**產品面的指標**

登記一張鑑定卡的**中位互動次數**。這個不用 AI 也能量——先量現在的基線
（依 `CardUploadPage.vue` 的流程，一張卡約是「搜尋字串 → 認縮圖 → 選變體 → 抄 8 位編號 → 打等級」）。
如果接了掃描之後這個數字沒有明顯下降，那不管辨識準確率多漂亮，這個功能都沒有解到它宣稱要解的問題。
