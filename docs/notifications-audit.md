# 通知完整性稽核

最後更新：2026-08-31

這份文件回答一個問題：**「會動到使用者的錢、卡、權限或義務的事，發生的當下他不在場 ——
他需要知道嗎？」** 底下的表就是逐一走過每一條這樣的路徑之後的答案。

表本身是交付物：新增任何會寫 `points_ledger`、改 `prizes.status`、改 `orders.status`、
改 `pool_settlements.status`、改 `sellers.tier`、改 `seller_verifications.status`
的程式碼時，要回來加一列。

---

## 判準

| 判定 | 條件 |
|---|---|
| **必須通知** | 影響他的錢、他的卡的歸屬、他能不能做某件事、或**他有一個有時限的義務要履行** |
| **不該通知** | 他自己剛剛按下按鈕造成的，而且當場就看得到結果 —— 那是雜訊，會把鈴鐺變成流水帳 |
| **邊界** | 同一個動作對兩造的意義不同。典型例：賣家自己按「我已寄出」不用通知他自己，**但要通知買家**（買家的鑑賞期時鐘從那一刻開始跑） |

### 兩種 refId 語意（選錯會洗版或漏發）

`notifications` 有唯一索引 `(user_id, kind, ref_id) where ref_id is not null`。

| 語意 | refId 綁什麼 | 前例 | 用在 |
|---|---|---|---|
| **一次性的事實**（知道了就好） | 那個實體的 id | `pools-service.ts` 寄存提醒綁 prize id | 結算釋放、退款、回收、審核結果 |
| **還沒修就要一直吵的狀態** | `key:日期` | `monitor.ts` 檢測警報綁 `check:日期` | 目前只有系統檢測 |
| **一次動作**（同一個實體可以合法地發生第二次） | 動作本身的 id | 這次新增：`admin_actions.id` | 賣家等級變更（可以來回升降） |

第三種是這次補出來的。賣家等級綁賣家 id 會讓「降級後再升回來」靜默消失，綁 tier
值也一樣 —— 只有「這一次後台動作」是唯一的。`audit()` 因此改成回傳 `admin_actions.id`。

### 沒有開新的 kind

`007_social.sql:50` 的白名單七個值（`draw` / `trade-offer` / `trade-result` /
`listing-sold` / `order` / `shipment` / `system`）**夠用**，所以沒有新增 migration。

不開新 kind 還有一個現實理由：前端的圖示與色調表在 `src/lib/social.ts` 與
`NotifyBell.vue`，新 kind 沒補進去就會走 `KINDS[k] ?? KINDS.system` 的退路，
渲染成灰色的「系統」—— 也就是說開了新 kind 卻拿不到新的視覺分辨，只多一支 migration。

## ⛔ 需要另外安排（動到別的 agent 的範圍）

以下六則判定為**必須通知**，但寫在這次不能碰的檔案裡。每一則都寫清楚要動哪裡。

| # | 通知 | 要動的檔案 | 建議的 refId | 為什麼非它不可 |
|---|---|---|---|---|
| A4 | 池揭曉 → 賣家：沒抽走的卡已解押回卡冊，可以再開池或上架 | `pools-service.ts`（`revealPool` / `releasePledgedCards`） | `pool-released:<poolId>`（一次性） | 解押只發生在揭曉那一刻，而那是掃描觸發的 |
| B4 | 賣家出貨 → 買家：鑑賞期開始跑，14 天沉默視同送達 | `routes/orders.ts` 的 `POST /:id/ship` | `order-shipped:<orderId>` | 那支端點是唯一知道「賣家剛按下出貨」的地方 |
| B5 | 買家確認收貨 → 賣家：貨款已入帳 | `orders-service.ts` 的 `settle()`（`status === 'completed'` 分支） | `order-completed:<orderId>` | 放在 `settle()` 才能同時涵蓋「買家按確認」與「鑑賞期滿自動完成」兩條路，不必寫兩份 |
| B6 | 鑑賞期滿自動完成 → 雙方 | 同 B5（`settle()` 已經涵蓋賣家側；買家側可加在同一處） | 同上 | 同上 |
| B7 | 逾期未出貨自動取消 → 買家退款、賣家保證金被沒收 | `orders-service.ts` 的 `settle()`（`forfeit` 分支） | `order-forfeit:<orderId>` | 沒收保證金的分錄就寫在那裡，通知跟著它才不會漏掉任何一條觸發路徑 |
| B8 | 買家開爭議 → 賣家 | `routes/orders.ts` 的 `POST /:id/dispute` | `order-disputed:<orderId>` | — |

共通的實作注意：

- `orders-service.ts` 的 `settle()` 跑在 `act()` 與 `sweep()` 的交易裡，
  比照 `pool-settlement.ts` 的 `refund()` 直接 `notify(..., tx)` 即可
  （在交易裡不能吞例外 —— Postgres 交易一旦 abort，後面的語句都會失敗）。
- `sweep()` 會被每一次讀取觸發，所以 refId **一定**要綁 orderId 這種穩定的鍵。
  `settle()` 本身沒有「有沒有真的改到」的守衛，靠的是 `applyDeadlines` 回傳同一個
  物件時就 `continue` —— 通知的冪等要交給唯一索引，不能靠呼叫次數。

### 為什麼「賣家證件通過」不說「現在可以開池了」

因為那對一半的賣家是假的。`/verifications/:id/review` 只改
`seller_verifications.status`，**不動 `sellers.tier`**，而開池的門檻讀的是 tier。
所以審核通過的措辭只講「這一份文件的結果」，開池權限由 E4 那一則各自說。

這件事本身值得後續處理：兩個狀態各自獨立、而使用者只感覺得到一個「我過了沒」。
不在這次的範圍（那是流程變更，不是通知）。

## 迴歸測試

`server/src/smoke.ts` 的「通知完整性」一節（25 條），加上散在接管與爭議兩段的 4 條。
每一則新通知都驗三件事：

1. **真的寫進 `notifications`** —— 端點回 `ok` 不算數
2. **refId 冪等** —— 重複觸發（掃描一天會跑很多次）只留一則
3. **link 指到前端真的存在的路由** —— 用一份路由白名單比對，而不是逐條 assert 字串

第 3 點有一條總攔截：「買家／賣家／賣場的通知沒有指向不存在的路由」會掃過那個帳號
**全部**的通知。`/wallet` 與 `/cards` 兩個死連結活了很久，就是因為從伺服器這一側
完全看不出來 —— 通知寫成功了、端點回 ok，只有使用者點下去會掉進 404。
白名單那份清單改動時要跟 `src/router/index.ts` 對一次。
