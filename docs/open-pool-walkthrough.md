## 步驟 7 — 經濟護欄的四種狀態

**我做了什麼**：兩張卡、票價 300、A 賞 1 張 + D 賞 99 張（共 100 籤，票收 30,000），
調整賞別買回價撞四種判定。

| 想撞的 | A / D 買回價 | 保底回饋 | 比率 | 畫面上的判定 | 送出鈕 |
| --- | --- | --- | --- | --- | --- |
| predatory | 5,000 / 10 | 5,990 | 20.0% | **不合格，無法開池** | `看看還差什麼` |
| ok | 6,000 / 91 | 15,009 | 50.0% | 合格 | **`開池上架`** |
| thin | 6,000 / 222 | 27,978 | 93.3% | 合格（＋警語） | **`開池上架`** |
| mint | 6,000 / 253 | 31,047 | 103.5% | **不合格，無法開池** | `看看還差什麼` |

四種都對，四種的說明都是完整的句子而不是代碼：

- predatory：「保底回饋率僅 20.0%，等於幾乎沒有保底，對玩家過於不利。」
- thin：「保底回饋率 93.3%，如果整池的卡都被買回，你只留得下不到 6.7% 的票收，扣掉運費與金流成本可能倒貼。」
- mint：「…宣告的買回價總和已經超過票收。整池抽完再全部買回，拿回來的比付出去的多 —— 這個池是一台印鈔機。」

而且每一種底下都跟著同一句釋義：
「把整池抽完、每一張都按賣家宣告的買回價收回來，能拿回票收的多少 —— 這是下限，不是平均。」

截圖 `17-econ-predatory.png` / `17-econ-ok.png` / `17-econ-thin.png` / `17-econ-mint.png`。

**這是問題嗎**：不是。**這一段是整條動線做得最好的地方**——
擋、提醒、放行三種待遇分得清楚，數字即時更新，被擋的時候知道是哪一格害的。

一個可以再想的：`thin`（93.3%）的判定標籤仍然寫「合格」，
綠色的合格章跟底下那句「可能倒貼」在同一張卡上，讀起來有一點互相抵消。**Low**。

### 附記：關於「按了沒反應」

## 步驟 10 — 送出之後：池在哪？點得過去嗎？

**我做了什麼**：按 `去看這個池`。

**實際發生什麼**：

### 🔴 P1（Critical）剛開好的池被標成「已完抽」

後端資料是：`status='committed'`、`totalTickets=100`、`remainingTickets=100`、`takenSeats=[]`、`openedAt=null`。
畫面上是：

- 池詳情頁標題列：**`300 點 / 抽　剩 100 / 100　已完抽`**（同一行自相矛盾）
- 抽卡面板整塊被換成 **`本池已完抽`**
- 大廳 `全部` 分頁：**找不到這個池**（`mine: 0`）
- 大廳 `已完抽` 分頁：**在這裡**（`mine: 2`），卡片上同時印著 `完抽` 和 `剩 100/100`

截圖 `20-pool-detail-committed.png`（393）、`D4-pool-committed-1280.png`（1280）、
`36-lobby-committed-card.png`（大廳卡片）、`22-lobby-filter-done.png`（篩選列）。

來源是把「不是 open」一律當成「完抽」：

- `src/pages/pool/PoolShell.vue:66` — `pool.status === 'open' ? '抽選中' : '已完抽'`
- `src/pages/pool/PoolShell.vue:102` 與 `src/pages/pool/PoolOverview.vue:77` — `本池已完抽`
- `src/pages/LobbyPage.vue:139–158` — 每一個分頁的述詞都是 `p.status === 'open'`，
  而 `done: p => p.status !== 'open'`

**這是問題嗎**：**是，Critical。** 三個理由：

1. 賣家剛剛被告知「系統取到外部亂數之後會自動開賣（通常幾分鐘內）」，
   然後點一下就看到自己的池寫著「已完抽」。那句解釋跟這個畫面互相否定，
   賣家沒辦法判斷剛剛到底成功了沒有。
2. 這不是一瞬間。後端的 `sweepPools` 是 **5 分鐘一輪**（`server/src/index.ts:178`），
   所以每一個新池都有最長 5 分鐘處在這個狀態。實測我的兩個池在 14:42 才被掃開。
3. **買家也看得到。** 這段時間裡新池不在 `全部`，只在 `已完抽`，
   還帶著「完抽」徽章。逛大廳的人不會點一個寫著完抽的池。
   這是直接吃掉新池開賣頭幾分鐘的曝光。

順帶：後端 `/v1/pools` 本來就會回 `committed` 的池（實測 16 個池裡兩個是我的），
所以這完全是前端的分類問題。

### 開賣之後就正常了

5 分鐘後 sweep 把兩個池推成 `open`，再看一次：

- 大廳 `全部`：找得到，卡片是 `300 點 / 抽　剩 100/100`（沒有完抽徽章）
- 賣家頁 `/sellers/u-885b858a0441`：`開過的池 2`，兩個池列在 `抽選中` 底下
- 池詳情：正常

截圖 `34-lobby-open.png`、`35-seller-store.png`。

所以「大廳／賣家頁看得到嗎」的答案是：**開賣之後看得到，開賣之前被標成完抽。**

一個小的：賣家頁寫「加入於 Mon Aug 31」——日期沒在地化。**Low**。

## 步驟 11 — 新賣家的首池上限

**我做了什麼**：兩次，各撞一邊。

**A. 籤數**（101 籤、票收 30,300）
即時試算全程顯示 `合格 / 保底回饋率 49.8%`，送出鈕顯示 `開池上架`。
按下去 → `403 FIRST_POOL_CAP`：

> 第一個池的上限是 100 籤、票收 100,000 點。這個池是 101 籤、票收 30,300 點。完成第一個池之後就會解除。

錯誤訊息量到 `y=574.7 / bottom=639.2 / vpH=852 / inView=true`。

**B. 票收**（100 籤 × 1,500 = 150,000）
同上，訊息換成「這個池是 100 籤、票收 150,000 點」。

截圖 `23-firstcap-tickets.png`、`23-firstcap-value.png`。

**這是問題嗎**：

**訊息本身很好**——講出兩個上限、講出你這池的兩個數字（讓你自己判斷是哪一個爆了）、
講出什麼時候會解除，而且顯示在視窗裡。

**但事前完全沒有預告，這是 Medium。**
`FIRST_POOL_TICKET_CAP = 100` / `FIRST_POOL_VALUE_CAP = 100_000` 就放在
`src/shared/pool-settlement.ts:100-101`，**但 `src/` 底下沒有任何一頁 import 它們**
（全 repo grep 只有那個定義檔本身）。
所以賣家挑完 101 張卡、填完賞別、看著即時試算說「合格」，
按下去才知道自己從第一步就超標了。這一頁其他每一條規則都是邊填邊講的，
只有這一條是送出才講。

**還有一個更小的**：「完成第一個池之後就會解除」沒有定義「完成」。
後端的定義是 `status in ('revealed','cancelled')`——也就是要**完抽並公布種子**。
我當時已經有三個 `committed` 的池，照字面讀會以為早該解除了。**Low**。

### 12b. 去登記一張卡 → 🔴 P2（Critical）登記完的卡永遠挑不到

**我做了什麼**：照它說的按 `去登記一張卡（登記完就會出現在卡冊）` → `/me/cards/upload`
→ 挑 `リザードンex SV4a-331` → 選 PSA → 填編號 → `登記進卡冊`。
`200 POST /v1/cardbook/upload`，導到 `/me/cards?new=pz-up-f2014c56301c`。

**實際發生什麼**：

| 我看的地方 | 它說什麼 |
| --- | --- |
| `/me/cards` | **持有 1 張**，分頁 `全部 1` / `在卡冊 1`，卡片列在那裡 |
| `/seller/new` 的卡冊分頁 | **從我的卡冊挑 0**，「卡冊裡沒有可以開池的卡」 |

截圖 `32-mycards.png`、`38-cardbook-contradiction.png`。

量到的東西：

```
CardPicker 打的是   GET /v1/prizes?status=stashed   →  {"items":[],"nextCursor":null}
卡冊頁打的是        GET /v1/prizes                  →  1 筆，status = "in_book"
GET /v1/prizes/summary → {"total":1,"counts":{"stashed":0,...,"in_book":1}}
```

- `src/components/CardPicker.vue:91` 寫死 `status: 'stashed'`。
- `server/src/routes/prizes.ts:21` 的 `STATUSES` 是
  `['stashed','listed','ship_requested','shipped','recycled','refunded']`——
  **沒有 `in_book`**，所以 `?status=in_book` 直接被 zod 擋成 400，連改參數都沒用。
- 而後端建池**本來就支援** `in_book` 的卡：
  `server/src/routes/pools.ts` 有一整段專門處理
  「自己名下、閒置在卡冊（`in_book`）的一列，重用那一列押進新池」。

**這是問題嗎**：**是，Critical。**

`stashed` 的意思是「從池裡抽中、寄存在保管庫」。
一個第一次來的賣家不可能有 `stashed` 的卡——他還沒抽過任何池。
所以**「從我的卡冊挑」對一個新賣家永遠是 0**，
而且他照著頁面指示去登記卡片之後**還是 0**。
兩條卡片來源實際上只有一條走得通。

而且畫面說的理由是錯的：「只有寄存中的卡能當獎品 —— 已上架或已出貨的卡不在這裡」，
但我這張卡既沒上架也沒出貨，它就是剛登記進卡冊的一張卡。

### 12c. 🔴 P3（Critical）鑑定編號對不上時，登記頁是一條死路

**我做了什麼**：登記 `リザードンex SV4a-331`（目錄卡號 `331/190`），
PSA 編號填 `STUB-OK-331`（stub 會回 `CardNumber: "331"`）。

**實際發生什麼**：`409 CERT_MISMATCH`

> PSA 查到的卡片跟你填的卡號對不上（PSA 是英文、目錄是日文，卡名無法直接比對）。**請確認是不是同一張卡，確認後再送出一次。**

我照它說的再送一次。同一個 409。第三次。同一個 409。

量到的：

```
attempt 1  409 CERT_MISMATCH   input[type=checkbox] 數量 = 0
attempt 2  409 CERT_MISMATCH   input[type=checkbox] 數量 = 0
attempt 3  409 CERT_MISMATCH   input[type=checkbox] 數量 = 0

409 之後整頁 top 200–900px 之間可點的東西：
["INPUT|number","INPUT|number","BUTTON|登記進卡冊","A|大廳","A|市場","A|抽選","A|卡冊","A|我的","A|會員條款","A|隱私權政策","BUTTON|查看清單"]
```

截圖 `29-upload-mismatch-deadend.png`。

**這是問題嗎**：**是，Critical。** 三層：

1. **訊息叫我做一件畫面上做不到的事。** 「確認後再送出一次」——
   頁面上沒有任何確認控制項。再送一次得到的是一模一樣的 409。
2. **它沒有給我判斷的材料。** 後端在 409 的 body 裡回了
   `mismatches: [{certNo, psaCardNumber:"331", psaSubject:"PIKACHU"}]`，
   頁面把它整個丟掉。我看不到 PSA 到底查到了什麼，
   就算有勾選框我也沒有東西可以拿來「確認」。
3. **後端其實留了出路，前端沒接。**
   `server/src/routes/cardbook.ts:53` 的 `UploadBody` 有 `certConfirmed: z.boolean().optional()`，
   `src/pages/CardUploadPage.vue` 全檔 grep 不到 `certConfirmed`、
   不到 `checkbox`、不到「確實是同一張」。
   （對照組：開池頁 `SellerNewPoolPage.vue` 對同一個錯誤**有**完整的確認流程。）

**而且這個 409 很可能是常態不是例外。**
`server/src/card-cert.ts:23–32` 的 `cardNumbersAgree` 是把兩邊的數字全部串起來比：

```
digits("331")      = "331"
digits("331/190")  = "331190"       →  不相等  →  mismatch
```

PSA 的 `CardNumber` 欄位對日版卡通常就是裸的號碼，
而我們目錄的 `cardNo` 是卡面印的 `編號/總數`。
我實測換成 `STUB-OK-331/190`（讓 PSA 回 `"331/190"`）就一次過。
也就是說：**只要 PSA 回的是不含總數的號碼，這條路就走不通，而那是常見情況。**
（這一點我只能用 stub + 讀 code 推斷，沒有真的 PSA 回應可以驗，
所以標「很可能是系統性的」而不是「一定是」。）

### 12d. 對照組：CERT_ALREADY_LISTED 做得很好

**我做了什麼**：先用另一個帳號（`u-seller`）登記 `STUB-OK-115/190`，
再用我的新賣家帳號登記同一個編號。

**實際發生什麼**：`409 CERT_ALREADY_LISTED`，訊息量到 `y=214.8 / inView=true`：

> 鑑定編號 STUB-OK-115/190 已經登記在別人名下 —— 同一張實體卡不能重複登記。如果這張卡是你在站外買到的，請到客服中心（/support）申請接管，附上時間戳照片證明卡在你手上。

**而且下面直接長出出口**：

> **這張卡真的在你手上嗎？**
> 如果你是在站外買到這張實體卡，可以申請把編號接管到你名下。通過之後這張卡就是你的，登記、開池與上架都不會再被擋。
> 〔申請接管 PSA #STUB-OK-115/190〕

那顆按鈕是 `/support/new?kind=takeover&certNo=STUB-OK-115/190&grader=PSA&from=upload`，
點過去工單頁的 `鑑定機構`、`鑑定編號`、`主旨` 三格**都已經填好了**。

截圖 `28-upload-dup-after.png`、`30-takeover-ticket.png`。

**這是問題嗎**：不是，這一段是模範。
也正因為它做得這麼完整，同一頁上的 `CERT_MISMATCH`（12c）沒有出口才格外突兀——
兩個錯誤隔壁而已，一個有出路一個死路。

### 12e. 這兩件事加起來的後果

`P2`（自己登記的卡挑不到）＋ `P3`（鑑定卡多半登記不進去）合起來是：

> **一個新賣家在 UI 上開出來的池，裡面不可能有任何一張帶鑑定編號的卡。**

理由：目錄挑到的卡沒有 `certNo`（獎項列上只有賞別／數量／參考價／買回價，沒有編號欄位），
而唯一能帶編號進池的路是卡冊，卡冊那條路是死的。
對一個叫「鑑定卡的交易中心」的平台，這是我在這條動線上找到最嚴重的一件事。
